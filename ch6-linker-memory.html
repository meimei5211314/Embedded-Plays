LMA 与 VMA：一个变量，两个地址

本章最核心的一对概念
VMA（运行地址）
程序运行时用这个地址访问变量。对 .data 来说，它在 RAM。
LMA（加载地址）
固件镜像里初值存放的位置。对 .data 来说，它在 Flash。
启动代码的职责
把 .data 从 Flash 的 LMA 拷到 RAM 的 VMA，再把 .bss 清零。漏掉任何一步，全局变量初值就会错。
/* .data 的加载域与执行域分离 */ _sidata = LOADADDR(.data); /* Flash 中的初值镜像 */ .data : { _sdata = .; *(.data*) _edata = .; } > RAM AT> FLASH /* VMA=RAM，LMA=FLASH */

如果漏掉 .data 搬运，会发生什么

故障表第一条
现象
上电后全局变量初值全乱，局部变量却看起来正常；某些配置结构体 magic 不对。
根因
自定义启动文件漏写拷贝循环，或链接脚本段名不匹配，_sidata 指向了错误位置。
定位
反汇编 Reset_Handler 确认拷贝循环存在；比对 _sidata 与 .data 的 LMA；在 map 文件里看符号地址。
记住：.bss 不需要从 Flash 搬运，但必须清零；未清零的 .bss 变量会继承上电前的 SRAM 随机值。复位后依赖“碰巧为 0”是典型的隐蔽 bug。

栈预算怎么算

不是拍脑袋
① 每函数用量
用 -fstack-usage 得到每个函数的帧大小，包括局部数组和对齐开销。
② 最坏调用链
从入口和每个 ISR 出发，沿调用图累加；ISR 嵌套还要加每层硬件入栈帧。
③ 安全系数
乘 1.5 左右，再用运行期水位线验证。余量低于 50% 就该扩栈或拆函数。

体积公式：Flash 占用 ≈ text + data（.data 的初值镜像）；RAM 占用 ≈ data + bss + heap + stack。不要只盯着 text。
Q1：为什么修改链接顺序会改变全局变量地址？

段收集顺序 = SECTIONS 书写顺序 + 通配符展开顺序（通常又是 .o 链接顺序）。链接器按这个顺序把输入段拼进输出段，所以变量相对位置会变。不要依赖地址顺序做逻辑判断，跨编译单元的全局初始化顺序更没有标准保证。

Q2：CCM 这么快，为什么不能把所有变量都放进去？

F407 的 CCM 只有 CPU 内核可达，DMA1/DMA2 都访问不到。把 DMA 缓冲放进去，典型症状是传输永远完不成或数据全零。用前查芯片总线矩阵；同理还有 i.MX6ULL 的 OCRAM、RK3588 的部分 SRAM。

Q3：.bss 为什么不在 Flash 里占空间？

.bss 只记录“需要多少零初始化空间”，启动时由代码把 RAM 清零；它不需要在固件镜像里存放一大段零。因此 Flash 体积通常看 text + data，而 RAM 体积看 data + bss。

Q4：--gc-sections 很省空间，能无脑开吗？

不能。GC 从 ENTRY 出发做可达性分析，向量表、配置表、注册表这类“没有直接代码引用”的段会被误删。必须配 KEEP，或者用 used 属性/显式引用把入口钉住。
