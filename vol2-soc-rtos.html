34.4 多核启动与一致性

  • 冷启动不对称：BootROM 固定从核 0 起，其余核停在 holding pen（WFI 循环），由 U-Boot/ATF 通过 PSCI 接口唤醒——这就是 Linux maxcpus=/cpu-hotplug 的底层机制；
  • big.LITTLE（RK3588）：A76+A55 异构，调度器按负载迁移任务；性能敏感线程用 sched_setaffinity 绑大核（第65章实操）；
  • DSU 一致性单元：多核共享 L3，缓存行 MESI 协议维护一致——所以 spinlock 在 A 核上不需要像 M 核那样关中断，但要防伪共享（结构体成员跨缓存行 padding）。

34.6 原理深挖：MMU 地址翻译的完整旅程

VA → 物理地址四级页表走查(AArch64, 48位VA, 4KB粒度)：
TTBR0_EL1 → L0 表 → L1(1GB 块) → L2(2MB 块) → L3(4KB 页) → PA
TLB 缓存前两级结果；miss 才走页表遍历(硬件 walker)
对嵌入式 BSP 的三个实际影响：
① 设备树 reg 的地址是【物理地址】——驱动 ioremap 后拿到的才是虚拟
② DMA 缓冲必须经一致性映射或 swiotlb 弹跳缓冲(ch26 对照)
③ 改页表属性(XN/缓存)要走 set_memory_xx 接口，手改 TTE 会踩 TLB 一致性
M 核工程师最常翻的车： 把物理地址当虚拟地址直接解引用 → imprecise abort

34.9 进阶话题四则

  • DSU 的 L3 共享与伪共享：多核共享 L3 下，跨核高频写的计数器要做 64B 对齐隔离——perf c2c 在 A 核上同样可用；
  • PSCI 的存在感：secondary core 启动/CPUIdle 全走 ATF——内核日志里 psci: probing 就是它在握手；
  • RISC-V 平台差异：无 GIC 对应物时中断控制器随厂商(CLINT/PLIC/APLIC)，BSP 移植工作量集中在 irqchip 驱动；
  • 混合关键性架构：A 核跑 Linux + 同片 M/R 核跑 RTOS(OpenAMP/rpmsg)——RK3588/I.MX8 双系都支持，是「既要又要」的标准解。

35.5 原理深挖：IVT/DCD 的字节级结构

IVT(Boot 头, 32 字节) 关键字段：
  header(0xD2 标签) | entry(入口地址) | dcd_ptr | boot_data_ptr | self
DCD(Device Configuration Data)： 一串「写寄存器命令」表
  [tag=0xCC][len][CCM_CCGR0 地址][值] ... —— 全是 DDR 初始化序列
烧写位置规则： SD 卡偏移 1KB(0x400) 放 IVT —— dd 写错偏移=不启动
imx-mkimage 工具链： mkimage_imx8 -ivt ... 把 uboot 打成可启动镜像
排查口诀： 上电无输出先 hexdump 卡首 2KB 确认 IVT 在位且 entry 合理。

  2. Sensor probe 顺序竞态：I2C4 上四颗同型号 sensor 地址相同靠 GPIO reset 分时释放——probe 顺序错导致两路共用一个驱动实例。对策：reset-gpios 时序+dts 别名固定顺序。
  3. 虚拟 ISP 与物理 ISP 绑定错：rkisp_vir 绑错物理核导致两路图像互相「串台」。对照官方 binding 表逐行核。
  4. IOMGU? IOMMU 页错误静默丢帧：NPU 输入用了未映射的用户态指针。一律 dma-buf fd 传递(ch85.5 教训)。
  5. CMA 不足偶发 RGA 分配失败：默认 CMA 太小。按 44A.5 核算显式声明并验证 /proc/meminfo CmaFree。
  6. NVMe 写入抖动引发丢帧：录像落盘与采集抢 AHB? 抢 PCIe/内存带宽。对策：录像写入限速+独立电源域+io scheduler=none。
  7. 大小核绑反：推理线程被调度到 A55 → fps 减半。taskset 固定 cpu4-7 并在 systemd unit 里写 CPUAffinity。
  8. 温度墙导致 fps 缓降：壳内 70℃ 触发 thermal throttle。对策：均热板改造+thermal zones 阈值主动降帧而非被动降频。
  9. eMMC 作为录像盘寿命崩塌：误把录像写到系统 eMMC。分区规划时用 udev 规则强制挂载点到 NVMe。
  10. 多摄时间戳不同步：四路各自 ISP 时间戳漂移 ~30ms。对策：统一取 CIF 时间戳基准+软件对齐插值；严格同步需外部触发线。

为什么选 H3 而不是更新的芯片？

② 生态： 全志 H3 是 Linux 主线社区支持最完善的国产 SoC 之一(ch37)

· 超迷你尺寸(~21×51mm)： 双排排针全引脚引出，无屏幕/无按键——纯核心板定位

· 无线： XR819 SDIO Wi-Fi(802.11 b/g/n)——无蓝牙(H3 无控制器)，IoT 用 WiFi 即可
· 供电： USB Micro OTG 单口(供电+数据复用)

45.2 RMS（Rate Monotonic Scheduling）

规则： 周期越短优先级越高（静态优先级）
可调度充分条件(n个任务)： Σ Ci/Ti ≤ n(2^(1/n)-1)
  n=1:1.0  n=2:0.828  n=3:0.779  n=∞:ln2≈0.693
含义： CPU 利用率低于 69% 时任意周期任务集必然可调度(RMS最优)
      超过阈值不代表不可行——需精确仿真，但风险自负
例： 三个任务 C/T = {0.5/1, 1/4, 2/10} → U=0.5+0.25+0.2=0.95 > 0.779
    充分条件失败 → 必须时间轴仿真验证是否真的可行

45.3 EDF（Earliest Deadline First）

  • 动态优先级：截止期最近的先跑，利用率可达 100%；
  • 代价：每次调度决策要比较 deadline；过载时行为雪崩式劣化（多米诺），而 RMS 过载只牺牲低优先级——可预测性上静态占优，这也是 FreeRTOS 只提供抢占式固定优先级的原因；
  • Zephyr 提供 EDF 调度器选项；Linux 的 SCHED_DEADLINE 即 EDF 变体（A核混合关键性场景）。

45.4 优先级翻转三幕剧（火星探路者号同款 Bug）

设定： 低L持有互斥锁M； 高H等M； 中M不需要M但优先级居中
第一幕： L拿锁运行 → 第二幕： H抢占L并阻塞在M → 第三幕：
        M(中)就绪并抢占了还在持锁的L！ → H被中优先级间接压制 = 无界阻塞 ★翻转
修复①优先级继承 PI： H等待期间临时提升L到H级别，L尽快放锁
修复②优先级天花板 PC： 任务拿锁瞬间直接升到「所有可能争用者的最高级」
     —— 阻塞上限确定化(一次临界区时长)，适合硬实时认证场景
FreeRTOS： xSemaphoreCreateMutex() 自带PI；

47.1 为什么是 PendSV？

上下文切换必须发生在没有任何 ISR 活动时。若在 SysTick 里直接切换，可能被高优先级 ISR 打断导致半切状态灾难。方案：SysTick 只置 NVIC->ICPR = PENDSVSET，PendSV 设为最低优先级——它必然最后执行且不会被打断（除非更低的，不存在）。一次 pending 多次也只执行一次，天然去重。

    mrs r0, psp                  ; ① 取当前任务的用户栈顶(硬件已自动压完8个core寄存器)
    isb
    ; ---- 保存软件部分现场 ----
    ldr r3, =pxCurrentTCB        ; r3=&当前TCB指针
    ldr r2, [r3]
    stmdb r0!, {r4-r11, r14}     ; ② 手动压 R4~R11 和 EXC_RETURN(LR)
                                 ;    (R0-R3,R12,PC,xPSR 已由硬件入栈)
    str r0, [r2]                 ; ③ 新栈顶存回 TCB->pxTopOfStack(偏移0!)
    ; ---- 进入临界区后做决策 ----
    stmdb sp!, {r3, r14}         ; 保护 r3/lr 于MSP
    bl vTaskSwitchContext        ; ★C函数： 选出下一个任务，更新 pxCurrentTCB
    ldmia sp!, {r3, r14}
    ; ---- 恢复新任务现场 ----
    ldr r1, [r3]                 ; r1=新任务的TCB
    ldr r0, [r1]                 ; r0=新任务的 pxTopOfStack
    ldmia r0!, {r4-r11, r14}     ; ④ 弹软件寄存器(含EXC_RETURN→lr)
    msr psp, r0                  ; ⑤ 写回PSP —— 注意此刻还没真正换栈!
    ; FPU懒保存处理(略)： 检查 lr bit4 决定是否恢复 FP 上下文
    bx r14                       ; ⑥ 异常返回： 硬件从PSP弹 R0-R3/R12/LR/PC/xPSR
                                 ;    PC=新任务的断点 → 世界已切换
💡 三阶段记忆法

存旧（硬件8个+软件9个→TCB）、选新（vTaskSwitchContext 纯C决策，含时间片轮转与tickless补偿）、载新（TCB→寄存器组→bx r14）。全程只碰 PSP 操作任务数据，MSP 只用于异常自身——这就是 ch21 双栈设计的兑现。

47.8 进阶话题四则

  • 为什么恢复时先 msr psp 再 bx lr：bx lr 触发异常返回序列从 PSP 弹硬件帧——顺序反了会从旧任务栈弹出新任务的 PC（灾难现场）；

50.3 Tickless Idle 深度解析

问题： 空闲时 SysTick 每1ms醒来一次 → CPU 无法进入深度睡眠。
tickless 方案：
① vPortSuppressTicksAndSleep(xExpectedIdleTime)：
   - 关SysTick，配置低功耗定时器(LPTIM/RTC闹钟)在下一个最早到期事件时唤醒
   - WFI 进入睡眠
   - 唤醒后算出实际睡眠 tick 数 → xTaskCatchUpTicks(n) 补账
② 补账精度三坑：
   a) LP时钟(32k LSE)与主时钟频差 → 用 RTC 校准值修正
   b) 唤醒响应延迟(WFI退出+时钟重启 ~几十µs) → 减去固定补偿
   c) 睡眠中被中断打断 → 该次实际只睡到中断点，剩余时间重新计算
③ 配置： configUSE_TICKLESS_IDLE=1 + 可选自定义 portSUPPRESS_TICKS_AND_SLEEP
实测收益： 1ms tick 下 idle 电流 ~2mA → tickless 后 ~50µA(不含外设)

50.4 低功耗架构模式（结合 ch29）

模式机制典型电流
Tickless Idle所有任务阻塞时自动深睡µA~百µA
Stop+RTC 定时vTaskSuspendAll 后手动进 Stop，RTC 唤醒重建调度几µA
Standby 冷启等效复位+备份域保状态（ch29 冷热启动识别）~2µA

决策树：需要毫秒级响应→Tickless；秒级响应→Stop+RTC；分钟级→Standby。混合设备常用「运行态 Tickless + 空闲窗口 Standby」两段式。

52.1 微内核哲学

宏内核(Linux)： 驱动/文件系统/网络全在内核态 —— 性能好，一个驱动崩溃=整机蓝屏
微内核(seL4)： 内核只留 IPC+调度+内存管理最小集，
              其余全部变成用户态进程(服务器) —— 驱动崩了重启即可
代价： 每次跨服务调用走 IPC(原比函数调用慢) → seL4 用极致优化把 IPC 压到
      ~1000 cycles 级，配合性能敏感路径直通(pass-through)设计弥补。

52.2 Capability 模型（核心创新）

传统 ACLCapability
「谁能访问什么」存在全局表里权限就是一把不可伪造的「钥匙」对象本身
持有资源=知道地址持有 cap 才能操作；地址无意义
权限回收困难撤销(revoke)父 cap 即级联回收整棵子树
/* CSpace: 进程的能力空间(一棵cap树)。典型操作： */
seL4_CPtr frame = ...;                          // 一个4KB物理页帧的cap
seL4_Error err = seL4_Frame_Map(frame, vspace_cap,
                    seL4_Page_GetAddress(frame), rights);
/* rights = seL4_CanRead | seL4_CanWrite (不给CanGrant就转赠不出去)
   内存安全由此构造性保证： 没有 cap 的内存区域在物理上无法被触碰 */
/* TCB/endpoint/notification/irq 全是 cap —— 统一的对象系统 */

52.3 形式化验证三层次

  1. 功能正确性：Isabelle/HOL 证明 C 实现符合抽象规约（ARM 版完整完成）；
  2. 完整性：证明用户态代码无法破坏内核不变量（no user-kernel privilege escalation）；
  3. 信息流安全：可配置证明机密性隔离（用于高保密场景）。

工程意义：认证成本从「黑盒测试堆证据」变为「数学定理导出」——航空 DO-178C、医疗 IEC 62304 高等级认证的降本利器。代价：写应用要遵守严格编程纪律（禁动态分配于关键段、显式内存布局）。

先自问，再翻讲义
  1. 启动链是逐级交接
    闭卷自问：DDR 初始化失败会停在哪一步，串口可能看到什么？
    展开答案要点

    BootROM → SPL → ATF → U-Boot → Kernel → init，每一级都为下一级准备运行环境并完成验签。

  2. 设备树描述硬件
    闭卷自问：驱动 probe 不执行，先查哪三个地方？
    展开答案要点

    compatible 匹配驱动，pinctrl/clock/regulator 提供资源，overlay 支持板级差异。

  3. 实时性是时间可预测
    闭卷自问：RMS 利用率 0.75 是否一定不可调度？
    展开答案要点

    RMS/EDF 判断可调度性，优先级翻转会让高优先级任务被中优先级拖住，PendSV 负责上下文切换。

  4. 内存策略决定确定性
    闭卷自问：为什么硬实时项目更偏爱静态分配？
    展开答案要点

    heap_1~5 的取舍、栈水位、tickless 与 SMP 都会改变最坏响应时间。

  5. 证据来自时间轴
    闭卷自问：如何用时间轴证明最坏响应时间？
    展开答案要点

    Tracealyzer/SystemView 记录任务切换、队列与中断，才能证明 deadline 而不是感觉良好。

  6. 内核选择是取舍
    闭卷自问：什么时候值得为隔离上微内核？
    展开答案要点

    FreeRTOS、RT-Thread、Zephyr 与 seL4 在生态、认证、隔离与学习成本上各有边界。

高频追问 · 先答后看

6 问
请说清 BootROM、SPL、ATF、U-Boot、Kernel 各自负责什么，验签发生在哪一级？

BootROM 是固化信任根，负责选择启动介质并验第一级镜像；SPL 初始化 DDR 等关键硬件；ATF 建立安全监控、PSCI 与安全世界；U-Boot 加载内核与设备树；Kernel 初始化子系统后执行 init。验签通常由 BootROM 与后续 verified boot 链逐级完成，具体位置取决于 SoC 方案。

设备树里的一个节点，如何最终调用到驱动的 probe？

内核解析 DTB 建立 device node，platform bus 遍历设备并用 compatible 与 of_match_table 匹配；匹配成功后解析 reg、中断、时钟、pinctrl 等资源并调用 probe。若 probe 未执行，先查 compatible、status 与依赖资源，再看 dmesg 中的 deferred probe。

FreeRTOS 为什么用 PendSV 做上下文切换？

PendSV 可以被设为最低优先级，确保切换发生在所有中断处理完之后，避免在中断中途切换任务栈。触发 PendSV 后，硬件自动保存部分寄存器，切换代码再用 EXC_RETURN 与 PSP 完成任务栈切换，从而把“保存现场”和“选择下一个任务”分离。

优先级翻转是怎么发生的？优先级继承和优先级天花板有什么区别？

低优先级任务持锁时被中优先级任务抢占，高优先级任务只能等待，形成翻转。优先级继承让持锁者临时继承等待者的高优先级，缩短阻塞；优先级天花板在任务持锁时直接提升到该锁的最高可能优先级，能提前预防。两者都要用时间轴验证临界区长度。

heap_1 到 heap_5 应该怎么选？

heap_1 只分配不释放，启动期分配最安全；heap_2 支持释放但不合并，容易碎片；heap_4 合并相邻空闲块，通用性最好；heap_5 支持多个不连续内存区；heap_3 包装标准 malloc，线程安全但时间不确定。硬实时项目优先静态分配或对象池，动态分配只放在初始化阶段。

RMS 的可调度性判据怎么用？超过上界怎么办？

n 个周期任务满足 U=ΣC/T ≤ n(2^(1/n)−1) 时 RMS 一定可调度，n 增大时上界趋近 69.3%。超过上界不代表一定失败，需要做精确响应时间分析或时间轴仿真；也可以拆分任务、缩短临界区、提高优先级区分度或改用 EDF。
