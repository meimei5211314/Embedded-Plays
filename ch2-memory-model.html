2.2

指针四层功力：从“地址”到“泛型”

指针不是玄学，它只是“带类型的地址”。类型决定步长，层级决定你能改谁。

实验：p 每次移动几字节？ uint32_t *p
p = buf + 3 地址 0x2000000C *p = 40 偏移 12 字节
p + 1 移动的是 sizeof(*p) 字节，不是 1 字节。类型就是“步长说明书”。
同一件事：解引用绝对地址 GPIOA_ODR

PA5
地址 0x40020014ODR = 0x00000000

位 5 为 1 时输出高电平。这里必须加 volatile，否则编译器可能把寄存器访问优化掉。

为什么数组参数一定要带长度退化

函数形参 void f(char a[100]) 中的 a 已退化为 char *，sizeof(a) 只是指针大小。函数无法知道你实际传了多大的数组，所以必须显式传 len。

寄存器映射的实战写法volatile

用宏封装绝对地址，既保留类型，又让代码可读。真正的工程会再用结构体把同一外设的寄存器组织起来，但底层仍是“地址 + 偏移 + 解引用”。

为什么不能只传 char *值传递

C 的参数是按值传递。传 char *p 进去，函数拿到的是指针的副本；副本改成新地址，调用者的 p 完全不知道。要修改 p 本身，必须把 &p（char**）传进去。

读法拆解从里到外

char *names[3]：先读 names，它是数组，元素是 char*。
char (*row)[16]：先读括号里的 *row，它是指针，指向 char[16]。括号改变结合顺序。

回调

定时器到期、串口收到一帧、按键中断，都可以注册一个函数指针，让底层在合适时机“回头调用”你的代码。

解耦

协议栈不需要知道业务函数的名字，只保存函数指针。换业务实现时，协议栈一行不用改。

排查

void* 是“无类型地址”，不能直接做算术；先转成 unsigned char* 再逐字节走，标准 C 里最稳。
L1 本质

指针保存地址；类型决定解引用时读几个字节、走一步多远。

L2 本质

指针的指针，让你能修改“指针本身”；数组退化让长度信息消失。

L3/L4 本质

函数指针把“行为”当数据传递；void* 把“类型”暂时擦除，换取通用性。

2.3

五个关键字：把“玄学”拆成语义

volatile 管可见性，const 管读写权限，static 管可见性与存储期，restrict 是优化承诺，inline 只是建议。

关键字

volatile

告诉编译器：这个变量可能被程序流之外的因素改变。每次使用都必须真实访存，禁止缓存到寄存器，也不得随意重排它自身的访问。

保证
可见性：读到的永远是当前内存 / 寄存器值。
不保证
原子性、内存屏障、多核顺序。读-改-写仍可能被打断。
该用
ISR 共享标志、MMIO 寄存器、多核共享变量。
// 中断里改，主循环里等volatile uint8_t g_rx_done;while(!g_rx_done){ /* 等一帧 */ }
实验：编译器会不会重复读？
硬件寄存器 · 0x40000000 0
CPU 读到的值 0 循环次数 0 状态 等待单步
当前没有 volatile：循环只会在最开始 load 一次，之后一直比较寄存器里的缓存值。
三者互不替代背这句就够
volatile

管可见性：每次都去读真实内存。

锁 / 关中断 / 原子指令

管原子性：让多步操作不被打断。

DMB / DSB / 编译器屏障

管顺序性：约束读写先后。

单字节标志、单生产者单消费者时，volatile 往往够用；计数器、结构体指针交换等多周期操作，必须再配原子或互斥手段。

const 的读法左定值，右定针
const int *p

值不可改：*p = 1 编译报错；p 可以指向别处。

int * const p

针不可改：p 不能换地址；*p 可以改。

const 只表达“不通过这个指针写”，不保证对象一定在 Flash。是否进 ROM，取决于链接脚本把 .rodata 放在哪。
static 三种用法

① 函数内：静态存储期，函数退出不销毁；② 文件级变量：内部链接，别的 .c 看不到；③ 修饰函数：内部链接，只在本文件可用。

restrict 是承诺

告诉编译器“这些指针不重叠”，允许更激进地优化。违背承诺就是 UB。DMA 缓冲区别名场景慎用，先用 profiler 证明热点再考虑。

inline 只是建议

现代编译器会自行决定是否内联。static inline 放头文件最稳；extern inline 的语义因标准而异，嵌入式工程尽量少碰。

2.4

结构体对齐与 packed：省字节还是省麻烦？

CPU 喜欢“按自然边界”访问。对齐是在用填充换速度；packed 是在用速度与可移植性换体积。

协议帧 Frame 的字节布局
sof1Boffset 0
pad1B填充
len2Boffset 2
crc4Boffset 4
sizeof = 8 offsetof(len) = 2 offsetof(crc) = 4 padding = 1B

默认对齐下，sof 后面补 1 字节，让 len 落在偶地址，crc 落在 4 字节边界。整个结构体按最大成员对齐，所以大小是 8。

packed 省了 1 字节，但成员可能非对齐。M0 等内核不支持非对齐访问，M7 上跨 Cache 行也会变慢；不同编译器对非对齐访问的处理并不一致。协议解析优先用 memcpy 搬到局部变量，再按字段读。
默认对齐是“让 CPU 好读”，字段偏移由 ABI 和对齐规则决定。协议帧、DMA 描述符等跨机格式，才需要精确控制布局。
两种写法，差一个字节offsetof 验证
/* 默认对齐 */typedef struct {    uint8_t  sof;   /* offset 0 */    uint16_t len;   /* offset 2，前面补 1B */    uint32_t crc;   /* offset 4 */} Frame;            /* sizeof = 8 */
/* packed：按 1 字节对齐，无填充 */#pragma pack(push, 1)typedef struct {    uint8_t  sof;   /* offset 0 */    uint16_t len;   /* offset 1 */    uint32_t crc;   /* offset 3 */} Frame;            /* sizeof = 7 */#pragma pack(pop)
别用位段直接解析网络字节不可移植
/* 位段顺序、端序依赖编译器与架构 */struct Flags { uint8_t mode : 3; uint8_t flag : 1; }; /* 跨机传输：手动移位组装，语义最明确 */frame.id = ((uint16_t)raw[0] << 8) | raw[1];
对齐三条军规嵌入式日常
DMA 缓冲

用 __attribute__((aligned(32))) 显式对齐；M7 Cache 行通常 32B。

栈

AAPCS 要求 8 字节对齐，M3+ 硬件自动保证；手写汇编要自己守。

切片

malloc 返回值已对齐，但数组切片后不再保证；送给 DMA / SIMD 前重新对齐。

为什么默认对齐更安全

CPU 对“自然对齐”的访问通常是一条指令；非对齐访问在部分内核要拆成多次字节访问，甚至直接触发 Fault。编译器生成 packed 结构体访问时会更保守，代码也可能变大。

扩展：柔性数组C99

struct msg{ uint16_t len; uint8_t payload[]; } 适合“变长包 + 单次分配”。分配时 malloc(sizeof(msg) + n)，payload 紧跟结构体尾部，避免二次分配和指针跳转。

2.5

未定义行为：编译器的“合法谋杀”

UB 不是“结果不确定”这么简单。编译器可以假设它永远不会发生，然后把你写的判界、检查全部删掉。

UB · 最难查

越界一格写入

for(i=0; i<=n; i++) a[i] = 0xFF; 多写的那一格会踩到相邻变量、栈帧里的保存寄存器，甚至返回地址。症状往往不在越界处出现。

你期待
最多多写一个字节，数组外的东西不该受影响。
实际
相邻数据被覆盖；可能当场正常，函数返回时才跳飞。
定位
开边界检查 / ASan、看 canary、用 GDB 观察栈帧，别只看崩溃点。

第一板斧：让警告变成错误Makefile

-Wall -Wextra -Werror。把“可能未初始化”“有符号/无符号比较”“数组越界”这类警告当编译错误，别让它们沉在日志里。

第二板斧：分层检测UB 三件套

主机单测全开 UBSan / ASan；CI 加 -fanalyzer；板级保留 MPU 哨兵兜底。三层各抓一类，不要指望一层通杀。

第三板斧：按表 ReviewCERT / MISRA

对照有符号溢出、移位越界、序列点、空指针、返回局部地址逐条过。UB 的特点不是“报错”，而是“有时正常”，所以必须靠流程抓。

规则记忆C99 §6.3.1.1

小于 int 的整型（char、short、uint8_t、uint16_t 等）参与运算时，一律先提升为 int（若 int 能表示其全部值）。运算在 int 域完成，赋值回小类型时才截断。所以：截断点在赋值，不在运算。

2.7

故障排障：把“诡异”拆成可验证的假设

加打印就好了、结构体乱码、中断标志看不见——每个症状背后都有明确的候选根因。

时序 / 未初始化

加打印就好了（Heisenbug）

根因候选：打印改变了时序，掩盖了竞态；或者未初始化变量恰好被打印语句覆盖。它不是“自愈”，只是证据被扰动。

定位路径
  1. 分别用 -O0 与 -O2 编译，比较复现率，确认是否与优化/时序相关。
  2. 静态扫描所有可能未初始化的路径；把局部变量初始化，再观察现象是否变化。
  3. 用逻辑分析仪抓真实时序，替代 printf。把“加打印就好”变成“用仪器定位竞态窗口”。
FAQ：volatile 还要加锁吗？高频追问

volatile 只保证每次都真实访存，不保证“多条指令期间不被打断”。单字节布尔标志 + 单生产者单消费者，volatile 往往够用；计数器、结构体指针交换等多周期操作，必须再配关中断、原子指令或互斥量。

口诀：volatile 管可见性，锁管原子性，屏障管顺序性。三者互不替代。
FAQ：为什么嵌入式普遍禁用动态内存？实时性

三个理由：碎片化会让设备长期运行后分配失败；分配耗时不确定，破坏实时性；泄漏难以察觉。替代方案：静态池、FreeRTOS heap_4、对象池 + 引用计数。确实需要时，限定“只在初始化阶段 malloc，运行期禁用”。

FAQ：如何快速判断大小端？一行代码
union { uint32_t u; uint8_t b[4]; } t = { 1 };bool little = (t.b[0] == 1);

ARM 默认小端（Cortex-A 可配置 BE8），网络字节序是大端。跨机协议里 htons / htonl 不是可选项；漏掉的表现常常是“数值对，但字节序错”。

② 分层定位

判读规则：在同一物理映射内从低到高应呈现 text < rodata < data ≈ bss << heap << stack。MCU 上代码在 Flash、变量在 SRAM，数值上通常 Flash 地址更低。

本章思考题先自己想，再展开
1. 写一行表达式判断整数是否为 2 的幂，并解释 v & (v-1) 的几何意义。

v && !(v & (v-1))。减 1 会把最低位的 1 变成 0，并把更低位全部变成 1；再与原值按位与，若结果为 0，说明原值只有一个 1。v=0 要单独排除。

2. volatile const uint32_t * 这种组合什么时候用？

只读状态寄存器。硬件会改变它的值，所以必须 volatile 每次真实读；软件不应该通过这个指针写它，所以加 const。典型写法：const volatile uint32_t *status = ...;

3. 画出含 3 个局部变量、1 次 malloc、1 次 puts 调用的函数栈帧，标出 SP 变化。

高地址到低地址：caller 栈帧 → f() 保存的 LR 与 R4~R11 → f() 的局部变量 / 对齐填充 → 调用 puts 时 puts 的栈帧 → SP（8 字节对齐）。栈整体向下生长；数组的正向越界却向高地址覆盖 f() 的保存区，两者别混。

4. 为什么“数组小越界”的崩溃点总在函数返回之后？

正向越界先覆盖相邻局部数据或保存的寄存器；若继续覆盖到保存的 LR/PC，写入瞬间通常没有症状。等函数返回、把被改坏的 LR 弹进 PC，CPU 才跳向非法地址，所以崩溃滞后。
