74.4 链路预算速算法（无线必会）

接收灵敏度(dBm) ≤ 发射功率(dBm) + 发射增益 - FSPL(距离) - 余量(10~20dB)
FSPL = 32.44 + 20lg(f_MHz) + 20lg(d_km)
例： LoRa SF7 @470MHz, TX=14dBm, 灵敏度-123dBm →
    允许路径损耗=137dB → d: 20lg d = 137-32.44-20lg470-余量15 ≈ 62.5 → d≈1.3km(城市)
    换 SF10(灵敏度-137) → 再加 ~28dB → 视距可达 20km+
结论记忆点： 每翻一倍距离需要 +6dB；穿墙每堵承重墙扣 10~15dB。

74.5 原理深挖：把「需求」翻译成「参数」的完整推演示例

命题： 「500 台电表，每台上报 1 次/天，每次 200B；电池目标 10 年」
① 流量： 500×200B/86400s ≈ 1.2B/s —— 任何无线都绰绰有余 → 瓶颈不在速率
② 能量： NB-IoT PSM 待机 ~3µA + 每日注网突发折算 ~15µA 均摊
        → 2400mAh/0.018mA ≈ 15 年 ✓（留温度衰减系数后 ~9 年 ✓）
③ LoRaWAN 对照： SF12 上报 airtime 2.4s × 占空比法规 → 单站日容量有限，
   500 台需 2~3 个信道组或压缩到 SF7~9（缩短距离换容量）
④ 结论矩阵： 无运营商覆盖→LoRa 多网关；有覆盖且不想建站→NB-IoT；
   需要本地闭环控制(无云端延迟)→LoRa Class B/C 直控。
—— 选型文档就应该长这样： 参数化推演，而不是名词罗列。

74A.2 转义方案对比（透明传输二进制）

方案机制开销适用
COBS 一致性成帧 ★保证帧内无 0x00，以 0x00 作分隔符最坏 +⌈len/254⌉，平均 ~0.5%串口/LoRa 等字节流信道首选
SLIP 式转义ESC(0xDB)+替换表最坏 ×2(全 0xDB 载荷)简单但最坏情况差
Base64/Hex 文本化整体编码+33%/×2AT 信道、调试便利优先时
不转义+长度定界靠 LEN 判界0TCP 等自带边界的可靠流
/* COBS 编码核心(解码对称)： */
size_t cobs_encode(const uint8_t*in,size_t n,uint8_t*out){
    uint8_t *code=&out[1]; size_t code_idx=0,zero=1;
    for(size_t i=0;i<n;i++){
        if(in[i]==0){ *code=zero? (uint8_t)(code_idx+1):0; /* 占位逻辑见原论文 */
                      code=out+(++code_idx); zero=1; }
        else out[++code_idx]=in[i];
    } *code=(uint8_t)(code_idx+1); return code_idx+2;
}
/* 工程提醒： COBS 后仍建议叠加 CRC——它解决「定界」不解决「损坏」*/

74A.4 可靠传输状态机：停等 vs 滑动窗口

决策树：
  上行遥测允许丢？ → QoS0 直发(ch80A 思想)
  指令必须达且低频(<1Hz)？ → 停等 ARQ: 发→等 ACK(200ms×3 重试)→放弃上报

      window=4~8；接收方校验失败丢弃后续直到失序块重传；

74A.5 版本兼容与灰度升级（十年寿命的关键）

  • 版本字段必设：帧头含 ver:4bit|flags:4bit；解析器对未知 ver 拒收并回错误码而非静默崩溃；
  • 只增不改原则：新字段一律追加在 payload 尾部+LEN 区分；旧解析器忽略尾部即可读新帧(前向兼容)；
  • 能力协商：握手报文交换双方支持的版本位图，取交集运行；
  • 灰度发布：新协议先开 flags 里的「试验位」给白名单设备；Broker/网关按 ver 分流解析器——固件回滚后老解析器依旧工作；
  • 废弃策略：字段删除走「标记 deprecated ≥2 个版本 → 统计使用率归零 → 物理移除」三步曲。

FAQ 避坑指南

T1：为什么我的帧在长 0xFF 序列后丢失同步？

无转义+纯 SOF 匹配的通病。改 COBS 或增加「SOF 前置静默要求」；接收端加最大帧长保护防假同步。

T2：新旧固件混跑期间通信大面积失败？

违反了「只增不改」。检查是否复用了旧字段的偏移语义；正确做法是新字段追加尾部并用 ver/flags 标记。

75.1 RTU 帧与时序铁律

帧格式： [ADDR 1B][FUNC 1B][DATA nB][CRC16 lo,hi]
功能码速查： 01 读线圈 | 03 读保持寄存器★ | 06 写单寄存器 | 0F/10 批量写 | 04 读输入
异常响应： FUNC|0x80 后跟异常码(01非法功能/02非法地址/03非法值/06忙...)

时序三参数(决定成败)：
  字符间隔 < T1.5 (1.5字符时间)： 否则从站判帧断裂
  帧间静默 ≥ T3.5 (3.5字符时间)： 帧边界判定唯一依据！
  @9600bps: T3.5 ≈ 3.64*11/9600 ≈ 4.17ms —— 主站轮询周期必须大于它
CRC16-MODBUS 计算序： 初值0xFFFF，低字节先传 —— 与标准CRC16差异常被搞错

typedef struct {
    uint8_t addr; uint16_t base; uint8_t nreg;
    int fail_cnt; bool offline; uint32_t next_poll_ms;
    uint16_t cache[64]; uint32_t last_ok_ms;
} slave_t;
void poll_engine(slave_t*slaves,int n,uint32_t now){
    for(int i=0;i<n;i++){
        slave_t*s=&slaves[i];
        if(now < s->next_poll_ms) continue;          // 未到轮询点(离线降频)
        modbus_set_slave(ctx,s->addr);
        int rc=modbus_read_registers(ctx,s->base,s->nreg,s->cache);
        if(rc==-1){
            if(++s->fail_cnt>=3){ s->offline=true; s->next_poll_ms=now+30000; }
        } else { s->fail_cnt=0; s->offline=false;
                 s->last_ok_ms=now; s->next_poll_ms=now+1000; }  // 正常1s
    }
}

76.2 总线卡死九步解锁法（背下来）

现象： SDA 被某从机钳在低位，主机无法产生 START。
根因： 从机在读数据中途被主机复位，还欠 N 个 bit 没吐完。
解锁步骤：
① 主机先关 I2C 外设，引脚切 GPIO
② SCL 手动输出 9 个时钟脉冲(让从机吐完当前字节)
③ 若 SDA 已释放 → 完成； 未释放再发一个 STOP 条件
④ 仍不行： 断电重启该器件电源(设计上预留 PMOS 开关★)
⑤ 都不行： 断整板电 —— 说明硬件设计缺电源开关，记入整改
预防设计三原则：
· 所有 I2C 器件纳入可控电源域或带 RESET 引脚
· 驱动初始化前先跑解锁序列
· 上拉电阻按总线电容计算(2.2k~4.7k@3.3V 常规)，别贪强上拉烧灌电流

76.6 完整工程：总线恢复子系统（bus_recover.c 可直接抄）

/* 在任何 I2C 外设初始化前调用；GPIO 编号按板级配置 */
int i2c_bus_recover(int scl_gpio,int sda_gpio){
    gpio_request_as_output(scl_gpio); gpio_set(scl_gpio,1);
    gpio_request_as_input(sda_gpio);
    if(gpio_get(sda_gpio)) return 0;              /* 总线健康，直接返回 */
    for(int i=0;i<9;i++){                          /* 最多放出一个字节(9bit) */
        gpio_set(scl_gpio,0); udelay(5);
        gpio_set(scl_gpio,1); udelay(5);
        if(gpio_get(sda_gpio)) break;              /* SDA 已释放 */
    }
    /* 发一个 STOP： SCL 低时拉低 SDA，再拉高 SCL，再拉高 SDA */
    gpio_dir_out(sda_gpio); gpio_set(sda_gpio,0); udelay(5);
    gpio_set(scl_gpio,1);   udelay(5);
    gpio_set(sda_gpio,1);   udelay(5);
    return gpio_get(sda_gpio)? 0 : -EBUSY;
}

77.1 SPI 时序四模式与 QSPI

模式判定口诀： 看器件手册第一颗时钟沿采样位置
  Mode0 (CPOL=0,CPHA=0)： 空闲低，第一个沿(上升)采样 —— 最常见★
  Mode3 (CPOL=1,CPHA=1)： 空闲高，第二个沿采样     —— Flash/屏常见
  判错症状： 数据整体左移/右移一位，像乱码但规律性强(ch19 解码对照)

QSPI 提速三级跳：
  单线 SPI(命令+数据都走MOSI) → Dual(2线数据) → Quad(4线) → 
  XIP(内存映射执行： 代码直接在Flash上跑，省拷贝)
  关键配置： dummy cycles 必须匹配器件(读快了没等够=全0xFF)
  STM32 QUADSPI/OCTOSPI 外设 + W25Q128 例： 4线@50MHz ≈ 25MB/s 实测

#define CMD_SECTOR_ERASE_4K 0x20

int flash_write_buf(uint32_t addr,const uint8_t*buf,uint32_t len){
    while(len){
        uint32_t page_off = addr & 0xFF;
        uint32_t chunk = min(256 - page_off, len);   /* 不跨页拆分 ★必做 */
        flash_wren();
        flash_cmd_addr_data(CMD_PAGE_PROGRAM,addr,buf,chunk);
        wait_busy();                                  /* tPP≈0.4~3ms */
        addr+=chunk; buf+=chunk; len-=chunk;
    }
}

77.4 文件系统落地三选一

  • Littlefs（MCU 首选★）：掉电一致设计、磨损均衡内建、RAM 占用小；配合 lfs_util 移植到任意块设备接口；

78.1 为什么 CAN 这么稳？

CAN 能成为工业与车场的骨干总线，靠的是三个精巧机制：

  • 多主无损仲裁：ID 越小优先级越高，显性 0 覆盖隐性 1——两站同时发送时按位竞争，输者自动变接收，帧不破坏零浪费；
  • 错误分级处理：CRC/ACK/格式错误 → 错误帧重发；错误计数器三级跳（Error Active → Passive → Bus Off）——坏节点自动隔离，不上累全网，这是工业可靠性的精髓；
  • 差分传输 + 终端 120Ω×2：抗共模干扰，40m@1Mbps / 500m@125kbps。
SOF11bit IDRTR控制（4b DLC）0~8B 数据15b CRCACKEOF
起始优先级仲裁远程/数据帧数据长度有效载荷校验应答帧结束
💡 CAN FD 的升级点

数据段可变速率（最高 8Mbps）+ 64B 载荷——仲裁段保持不变，所以经典 CAN 的仲裁与错误机制全部继承，存量设计可平滑升级。

78.6 原理深挖：错误计数与 Bus-Off 的恢复时序

💡 TEC/REC 错误计数速记

TEC（发送错误计数）/ REC（接收）：成功收发 → 计数 −1（至 0）；错误 → +8。简化记忆：主错误 +8，成功 −1；TEC > 255 → BUS-OFF（节点离线，只听不说）。

Bus-Off 后的两种恢复策略：

  1. 自动恢复（内核 can restart-ms 参数）：等 128×11 个隐性位序列自动回网；
  2. 受控重启（推荐）：应用层显式 ip link set canX type can restart——配合退避计时，避免「坏节点反复冲击总线」。
⚠️ 工程纪律

bus-off 必须上报云端并记录 TEC 现场——它几乎总是物理层问题的第一信号（线缆/终端电阻/干扰），不要只当软件事件处理。

81.3 稳定性工程化四指标

81.6 原理深挖：一次完整关联的字节级旅程

Probe Req(广播/定向) → Probe Resp(能力集:速率/HT/VHT/RM)
→ Auth(Open/SAE) → Assoc Req(声明能力子集) → Assoc Resp(status=0)
→ EAPOL 4-Way(PTK 派生; WPA3 则 SAE 握手在前) → Group Key Handshake
→ DHCP(DORA 四步) → ARP 网关 → 可用
抓包判读锚点(Wireshark wlan 过滤器)：
· 卡在 Assoc Resp status≠0 → AP 拒绝：看 reason(17=AP 满/1=能力不匹配)
· 4-Way 第 2 包后无第 3 包 → PSK 错误(AP 静默丢弃 M3)
· DHCP Discover 无 Offer → 广播域问题或 VLAN 未放行

82.1 GATT 数据建模方法论

设计原则：一个「可独立订阅的数据流」= 一个 Characteristic。环境传感服务的参考布局：

Service: 环境传感 FFE0
 ├ Char FFE1 Temp      Read|Notify    (int16 x0.01°C)
 ├ Char FFE2 Humidity  Read|Notify
 └ Char FFE3 Ctrl      Write|WriteNR  (命令字节+参数)

Descriptor：CCCD(0x2902) 自动生成——Notify 开关由客户端写它控制。

💡 MTU 吞吐账本

ATT 默认 MTU 23 → 有效载荷仅 20B；协商到 247 后每个 conn interval（15ms）可发多个包；DLE + 2M PHY 理论 ~1.4Mbps，实际 iOS/Android 平台约 100~700KB/s。高吞吐设计三招：减少每包开销 + 批量特征 + 客户端 ACK 窗口管理。

82.3 OTA DFU 两流派

方案机制适用
Nordic DFU(SMP/mcuboot manager)包签名验证+分片传输+回滚 —— mcuboot 蓝牙传输版nRF52/Zephyr 生态 ★成熟

自定义 DFU 协议骨架（可直接抄）：

控制口命令： [CMD_START][total_len,crc] → 回 [ACK,chunk_size]
            [CMD_DATA][seq,data...]     → 每 N 包回 CRC 校验点
            [CMD_END]  → 设备校验整体CRC → 写标志位重启 bootloader
  • 可靠性三件套：seq 序号去重 / 滑动窗口流控 / 断点续传（存已收长度到 NVS）；
  • 安全两件套：镜像签名（ECDSA）+ 版本单调递增防降级攻击。

82.10 实战深化①：BLE 大数据分块流传输模式

需求：经 BLE 传 100KB 日志/波形——远超单包能力。生产验证过的成熟模式：

  1. 控制特征(C)：客户端写 {CMD_START, total_len, crc}；
  2. 数据特征(D)：服务端按「每 conn interval 尽量多发」推送分块，每块头 [seq:2B][len:1B][payload≤MTU-3]；
  3. 流控：客户端按接收速率周期性写 C {CREDIT,n}——慢了服务端暂停；
  4. 完成：CRC 校验 → C {ACK,final}；断点续传记录 last_seq 于 NVS。

85.5 原理深挖：一次 MMIO 写的硬件旅程

CPU iowrite32 → 总线桥转换 Memory Write TLP →
  链路层加序号+LCRC → 物理层 128b/130b 编码 → 对端校验回 ACK(隐式)
关键推论：
① Posted write 不等响应——写完即返回，错误异步上报(AER) —— 
   「写成功了但设备没收到」的排查要靠读回验证
② 读是 Non-Posted： 同步等待 Completion——延迟高但结果可靠
③ DMA 方向： 设备主动读写内存，需 IOMMU 映射或 swiotlb 弹跳——
   64 位地址能力(dma_set_mask_and_coherent)没设对会静默失败

86.7 原理深挖：PTA/共存接口的工作原理

Packet Traffic Arbitration(PTA) 两射频芯片间的「交通信号灯」：
· 请求线： 射频 A 要发射时拉 REQUEST + 优先级位
· 判决： 共存控制器按优先级/正在进行的包决定 GRANT
· 状态线： 告知对方「我在收高优先级包，勿扰」
软件侧对应物(单芯片 combo)：
  ESP32 的 coexist 组件自动仲裁——但参数可调：
  wifi 静默期保护 BLE 连接事件 / BLE 让路给 WiFi TXOP
没有硬件共存接口的板子 → 只能纯软件时分：
  全局调度器把 LoRa/Cat.1 发射窗口避开 BLE conn interval(ch86.4 清单第①层)

 [boot 48K][slot0 432K][slot1 432K][scratch 64K][param 16K]
核心流程：
 App 运行中收固件 → 校验包头 → 写 slot1 → param 标 TEST
 → 重启 → MCUboot 验签(ECDSA-P256)+哈希 → swap 交换两 slot
 → 新固件自检 OK 后 imgtool confirm → 否则 N 次重启内自动 revert

2️⃣ 关键实现挑战与解法

挑战解法要点
swap 中断电一致性MCUboot 的 swap 算法在 param 区写状态机日志，每步幂等——移植时严格保留其 trailer 结构
F407 扇区大导致擦写慢下载阶段边收边写 slot1（扇区对齐缓冲），重启后才做校验，用户无感

多版本依赖管理imgtool dependencies 字段+设备端版本比较逻辑

  1. 总线是约束下的选择
    闭卷自问：为什么长距离多点场景通常不用 I²C？
    展开答案要点

    距离、速率、节点数、EMI、供电、成本与生态共同决定选型，单看参数表没有意义。

  2. 协议要能活十年
    闭卷自问：CRC 校验通过是否说明帧一定可信？
    展开答案要点

    帧结构、转义、CRC、ARQ 与版本兼容，决定协议能否演进而不互相打架。

  3. 电气问题常伪装成协议问题
    闭卷自问：I²C 从机把 SDA 拉死后如何恢复？
    展开答案要点

    上拉、时钟拉伸、终端电阻、共模与地电位，都会表现成 NACK、丢帧或校验错。

  4. 无线是共享介质的博弈
    闭卷自问：WiFi 一开，BLE 丢包为什么上升？
    展开答案要点

    WiFi/BLE/LoRa/NB-IoT 的共存、占空比、重传与功耗，必须靠空口证据判断。

  5. 项目交付靠验收
    闭卷自问：如何证明你的网关连续 24 小时稳定？
    展开答案要点

    需求、架构、实现、测试、演示与复盘，缺一项都只是“跑通过”。

  6. 量产门禁在安全与工装
    闭卷自问：安全启动的信任根为什么必须不可改？
    展开答案要点

    Secure Boot、密钥生命周期、HIL 与产测，决定产品能否规模复制。

面对一个新项目，你如何给出有理由的总线选型？

先列约束：距离、速率、节点数、实时性、EMI、供电、成本与生态；再用总线能力表做过滤，而不是只看峰值速率。最后用示波器/逻辑分析仪或空口抓包验证物理层与协议层，记录选型假设。

I²C 总线锁死的典型原因是什么？如何恢复？

从机在传输中途复位或掉电，可能持续把 SDA 拉低，主机无法产生 STOP。恢复方法是主机切换 GPIO，发送最多 9 个 SCL 脉冲再发 STOP，然后硬件复位从机；同时检查上拉阻值、时钟拉伸与地址冲突，避免再次发生。

CAN 的仲裁与 CAN FD 的关键变化是什么？

CAN 按 ID 逐位仲裁，显性位覆盖隐性位，ID 越小优先级越高，失败方自动退让而不破坏帧。CAN FD 提高数据段速率（BRS）、扩展 DLC/CRC 并支持更大载荷，但需要收发器、拓扑与控制器共同支持；ESI 用于指示错误状态。

BLE 的 GATT OTA 一般怎样组织？

连接后发现 OTA 服务与特征，使能通知；通过控制点开始升级，按偏移分包写入数据并校验；完成后校验签名、切换 bootloader 提交镜像并重启验证。失败要能回滚，且要处理断连续传与重复包。

Secure Boot 的信任链与密钥生命周期怎么设计？

从不可改的 BootROM/OTP 信任根开始，逐级校验下一级 bootloader 与应用的签名，任何一级失败就停止。私钥离线保存或放 HSM，设备侧只存公钥或对称密钥于安全元件；同时设计生成、注入、轮换、吊销与备份流程。

Modbus RTU 的 CRC 怎么计算？为什么经常有人校验失败？

CRC-16/Modbus 初值 0xFFFF，逐字节异或后右移 8 次，LSB 为 1 时异或 0xA001，结果低字节先发。常见错误是字节序反了、把 CRC 自身纳入计算、帧边界错或用了 CRC-16/CCITT 的参数。
