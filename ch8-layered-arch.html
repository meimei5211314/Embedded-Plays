分层架构与设计模式

模块化不是“多建几个文件夹”，而是让依赖有方向、让硬件有边界、让替换有成本。这一章把 C 语言的接口注入、三种最高频模式和一个可编译期检查的依赖规范，变成能直接搬进项目的骨架。

这一层负责什么

点击左侧层
App 层

只写业务编排：采集、判断、上报、状态迁移。它应该能在 PC 上跑单元测试，不需要真实硬件。

允许：sensor_itf.h禁止：HAL_ / LL_
唯一知道芯片型号的地方：board.c / main.c 的组装函数。它把具体驱动实例注入给 App；换 MCU 时只改驱动层和 board 文件，App 一行不动。
“接口头文件 + 多实现 + 注册注入”：C 语言没有虚函数，但 struct 里放函数指针，效果就是一张手写 vtable。接口头不包含任何寄存器地址、HAL 类型或芯片型号。
可编译期检查：把驱动头文件移出 App 的 include path，App 一旦直接 include drv_sht31.h 就编译失败；再配合 CI 的 grep 门禁，形成“技术 + 流程”双保险。
依赖方向

App → Service → Interface → Driver。接口层被上下同时依赖，但接口本身不依赖任何一方；运行时由 board 把实现注入。

换芯片的半径

理想状态：换 MCU 只改 drv_*.c 和 board.c；Service/App 的编译单元和测试用例不变。

测试的收益

接口是天然的 mock 点。第 9 章 Unity 测试会用 mock_sensor 替换真实驱动，在主机上覆盖业务分支。

8.2 / 8.8 · 依赖倒置

App 只认识函数指针表，不认识传感器型号

切换驱动时，board 换一个实例，App 的编译结果不变。点“读取温度”调用同一个 read 指针，观察三种实现返回不同结果——这就是可替换性。

接口与组装

C 语言的依赖倒置
/* sensor_itf.h：纯抽象，无硬件痕迹 */
typedef struct sensor_ops sensor_itf_t;
struct sensor_ops {
  uint16_t api_version;   /* 首成员：运行期校验 */
  int (*read)(sensor_itf_t *self, float *out);
  int (*selftest)(sensor_itf_t *self);
};

/* drv_sht31.c：具体实现 */
static int sht_read(sensor_itf_t *self, float *out) {
  /* I2C 读取、CRC、换算，全在这里 */
}
const sensor_itf_t g_sensor_sht31 = {
  .api_version = 1,
  .read = sht_read, .selftest = sht_selftest
};

/* board.c：唯一知道型号的地方 */
void board_init(void) {
  app_init((sensor_itf_t *)&g_sensor_sht31);
}
函数指针慢吗？F407 上一次间接调用约 9 周期，虚表约 11 周期，而一次 UART 事务是毫秒级。架构抽象的成本只在 PID 内环这类微秒级路径才需要“开天窗”直连。
接口版本：itf 结构体第一个成员放 api_version，运行期校验，防止 OTA 后新旧驱动错配。这是 IAP 场景常见事故的廉价保险。
8.3 · 高频模式三连（上）

观察者负责“通知”，队列负责“解耦”

同步观察者适合低延迟、短回调；ISR 与慢任务之间必须用生产者消费者队列。两个小实验都围绕一个问题：回调 / 队列满的时候，系统如何保持可预测？

① 观察者：一对多广播

点击发布
待发布：订阅者默认是“日志”和“显示”，云连接未订阅。
for (obs_t *o = ps->subs[topic]; o; o = o->next)
  o->cb(topic, data, o->ctx); /* 同步派发 */
同步回调的红线：回调里不要做阻塞 IO、不要拿同一把锁、不要假设自己运行在中断上下文。耗时或可能重入的回调应改为“投递到邮箱 / 队列”，异步化后再处理。

② 生产者消费者：ISR → 队列 → 任务

容量 4
FreeRTOS Queue · 单生产者 / 单消费者
空闲：xQueueSendFromISR 只把事件放进队列，解码与业务处理留给任务。
void UART_IRQHandler(void) {
  evt_t e = decode_isr();
  xQueueSendFromISR(q_evt, &e, NULL);
}
while (xQueueReceive(q_evt, &e, portMAX_DELAY))
  handle(&e);
队列满策略必须写清楚：丢弃最新 + 计数、覆盖最旧、还是阻塞等待？三者对实时性的影响完全不同。未定义策略的队列，就是一颗随机丢事件的定时炸弹。
8.3 / 8.4 · 代理与模块规范

给丑陋的 HAL 包一张“语义脸”

代理层负责锁、超时、错误码映射和重试，把 HAL 的句柄、状态枚举、毫秒换算收敛在一个文件里。点“调用 uart_write”走一遍完整路径，再注入一次超时。

uart_write 的代理路径

4 步 · 可注入超时
01uart_lock(d)
拿设备锁，防止多任务并发写同一串口
02HAL_UART_Transmit()
把毫秒超时换算成 tick，调用 HAL
03uart_unlock(d)
无论成功失败都必须释放锁
04map_err(s)
HAL 状态 → 项目统一错误码（0 / -ETIMEDOUT / -EIO）
待调用：App 只需要一行 uart_write()，不需要知道 HAL 句柄和 tick 换算。
门面 vs 代理：门面（facade）简化接口，代理（proxy）在调用前后加控制。这里两者合一：一行语义 API + 锁/超时/错误映射。真实项目里可拆成 uart_port 与 uart_bus 两层。

模块规范六条

贴墙上
① 一个对外头文件xxx.h 是契约；私有声明放 xxx_internal.h，不暴露给上层。
② 统一错误码对外 API 返回 int：0 成功，负数失败；errno 风格便于日志与重试。
③ 头文件不放变量全局状态封装为 get/set 或上下文指针，避免每个编译单元各有一份副本。
④ 初始化两段式xxx_early() 做时钟级，xxx_open() 做业务级；顺序集中在 init 表。
⑤ 延时走统一接口禁止裸循环 delay；统一 delay_ms() 才能在 RTOS / 裸机间移植。
⑥ 自带自测入口#ifdef MODULE_SELFTEST，让每个模块能在产线或 CI 里单独验证。
/* 代理前：App 里到处是 HAL 细节 */
HAL_UART_Transmit(&huart2, buf, len, 100);

/* 代理后：语义清晰、可测试、可替换 */
int rc = uart_write(UART_DEBUG, buf, len, 100);
if (rc == -ETIMEDOUT) retry_or_log();
门禁的度：grep 规则太严会催生“绕路 hack”。保留白名单注释 // ARCH-ALLOW: reason，CI 解析豁免并要求评审确认；规则要服务于架构，而不是变成新的形式主义。
8.6 / 8.7 / Lab L8-1 · 初始化与成本

初始化顺序不该靠“文件刚好被链接进来”

把每个模块的初始化函数登记到自定义段，链接器按优先级排序，main 只遍历一次。先按表跑一遍，再按文件顺序跑一遍，看依赖缺失如何让启动失败。

init 表执行顺序

5 个模块

依赖关系：clock → sensor / storage；storage → net；sensor + storage + net → app。优先级只是排序，依赖校验仍然要显式做；两者缺一不可。

链接器自动收集

RT-Thread INIT_EXPORT 原理
/* 注册宏：带优先级字节放进 .init_tab */
#define INIT_FN(prio, fn) \
  static const init_entry_t __init_##fn \
  __attribute__((used, section(".init_tab." #prio))) \
  = { prio, fn };

typedef struct {
  uint8_t prio; void (*fn)(void);
} init_entry_t;

INIT_FN(10, clock_init);
INIT_FN(20, sensor_init);
/* ...各模块文件各一行... */

/* ld：按段名排序 = 按优先级排序 */
.init_tab : {
  KEEP(*(.init_tab.0*));
  KEEP(*(.init_tab.1*));
} > FLASH
/* main：遍历函数指针表 */
for (p = __init_start; p < __init_end; p++)
  p->fn();
优点：新增模块零改 main，顺序集中可审查。代价：依赖链接脚本和段名规范；被 gc-sections 误删时要 KEEP；跨优先级依赖仍需运行期校验。
