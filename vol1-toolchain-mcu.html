💡 newlib-nano 与 printf 体积

完整 newlib 的 printf 带 float/locale 约 40KB+。--specs=nano.specs 换精简版省一半；再配合 syscalls 桩（重定向 _write 到串口）。浮点格式化需要额外 -u _printf_float 才启用——不加它 printf("%f") 输出空白是新手第一大坑。

10.2 四阶段流水线与排错映射

gcc -E main.c -o main.i     # 预处理：宏展开/头文件 —— 「宏展开结果看这里」
gcc -S main.i -o main.s     # 编译：生成汇编 —— 「优化到底干了什么看这里」
gcc -c main.s -o main.o     # 汇编：生成机器码
gcc main.o -o main.elf ...  # 链接：符号解析/重定位 —— 「undefined reference 看这里」

一步到位等价于： gcc -g -O2 -mcpu=cortex-m4 -mthumb -T link.ld main.c startup.s -o fw.elf

10.3 优化等级与危险选项

选项行为建议
-O0不优化，调试体验最佳Debug 默认
-Og保留调试友好性的适度优化日常开发推荐折中
-Os体积优先Flash 紧张的量产构建
-O2速度优先，激进假设量产主流；务必配齐 volatile/屏障
-O3/-Ofast更激进甚至违反标准的数学变换DSP 循环局部慎用；-Ofast 含 -ffast-math 破坏 IEEE 语义
-flto全程序优化，跨文件内联体积再省 5~15%；注意与部分汇编/预编译库兼容性

10.4 -O2 经典翻车案例集

/* 案例1：忙等待标志没加volatile —— -O2下while变if死循环 */
while(!flag_done){}          /* flag_done 应声明 volatile，或改用事件通知 */

/* 案例2：延迟循环被整体删除 —— 空循环无可观测副作用 */
for(volatile int i=0;i<10000;i++);   /* volatile救活；正式项目请用定时器 */

/* 案例3：别名违规 —— GCC假定float*和uint32_t*不指同一处 */
float f=1.5f; uint32_t u=*(uint32_t*)&f;   /* UB！ */
/* 正确： memcpy(&u,&f,4);  或 C99 union 整体访问 */

/* 案例4：strict aliasing下的自省优化 —— memcpy被当作永不重叠 */
uint8_t tmp[N]; memcpy(tmp,buf,N); memcpy(buf,tmp,N);   /* 可能被优化没了 */
/* 移位语义请用 memmove */

10.5 有用的冷门选项

-ffunction-sections -fdata-sections + -Wl,--gc-sections  # 未引用代码全裁剪
-fstack-usage                 # 每个.c旁生成.su，函数栈用量一目了然(ch06)
-Wl,-Map=fw.map,--cref        # 符号交叉引用表
-fno-common                   # GCC10起默认；避免tentative definition重复定义
--specs=nosys.specs           # 裸机无syscall桩（配合nano）
-save-temps=obj               # 保留.i/.s中间产物便于排查
-gdwarf-3 -g3                 # 带宏定义信息，GDB可查 #define

10.7 原理深挖：链接顺序与归组语法

# 为什么库要放在 .o 之后？
gcc main.o -lm        # ✅ 先解析 main.o 的未决符号，再让 libm 兑现
gcc -lm main.o        # ❌ 扫描 libm 时无人需要它 → 被丢弃 → undefined reference
# 归档内部同理： 单个 .a 只按需取成员；循环依赖用：
gcc main.o -Wl,--start-group liba.a libb.a -Wl,--end-group   # 代价：可能多链入成员
# 强制拉起未被引用的目标文件（驱动自注册场景）：
-Wl,-u,my_driver_init   或源码 __attribute__((used)) + KEEP() 双保险

10.9 进阶话题四则

  • _sbrk 与堆的真相：newlib 的 malloc 最终调 _sbrk(increment) 向上挪 _end 符号——重定向它即接管全部动态内存（ch49 heap_3 的底层）；
  • --specs=nano.specs 与浮点的组合矩阵：printf_float 开销约 +6KB；只需 %f 打印日志时可用自定义 ftoa 替代更省；
  • -flto 与中断向量的恩怨LTO 后跨文件内联可能把 ISR 函数体折叠进调用点导致向量符号消失——向量段 KEEP + used 属性是唯一可靠解；
  • 交叉工具链从哪来：Arm GNU Toolchain 官方包（版本最稳）/ xPack（CI 友好）/ Buildroot 自建（完全可控但维护成本高）——团队统一来源比选哪家更重要。

11.1 生产级 Makefile 骨架（可直接抄）

TARGET := fw
BUILD  := build
CROSS  := arm-none-eabi-
CC := $(CROSS)gcc
CPUFLAGS := -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard
CFLAGS := $(CPUFLAGS) -std=c11 -g3 -O2 -Wall -Wextra -Werror \
          -ffunction-sections -fdata-sections \
          -I Core/Inc -I App -I Drivers/CMSIS/Include
LDFLAGS := $(CPUFLAGS) -specs=nano.specs -specs=nosys.specs \
           -T link.ld -Wl,--gc-sections -Wl,-Map=$(BUILD)/$(TARGET).map

SRCS := $(shell find Core App Bsp -name '*.c')
OBJS := $(patsubst %.c,$(BUILD)/%.o,$(SRCS))

all: $(BUILD)/$(TARGET).elf $(BUILD)/$(TARGET).bin

$(BUILD)/%.o: %.c
	@mkdir -p $(dir $@)
	$(CC) -c $(CFLAGS) -MMD -MP $< -o $@      # -MMD 自动生成 .d 依赖

$(BUILD)/$(TARGET).elf: $(OBJS)
	$(CC) $^ $(LDFLAGS) -o $@

$(BUILD)/%.bin: %.elf
	$(CROSS)objcopy -O binary $< $@

flash: all
	openocd -f board/st_nucleo_f4.cfg -c "program build/fw.elf verify reset exit"

clean: ; rm -rf $(BUILD)
-include $(shell find $(BUILD) -name '*.d')   # 头文件改动也能触发重编

11.2 CMake 交叉编译三件套

# ---- arm-toolchain.cmake ----
set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)
set(CMAKE_C_COMPILER   arm-none-eabi-gcc)
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)  # 跳过可执行试编译(无OS)
add_compile_options(-mcpu=cortex-m4 -mthumb)

# ---- CMakeLists.txt ----
cmake_minimum_required(VERSION 3.20)
project(fw C)
set(CMAKE_EXECUTABLE_SUFFIX ".elf")
file(GLOB_RECURSE SRCS Core/*.c App/*.c Bsp/*.c)
add_executable(fw ${SRCS})
target_include_directories(fw PRIVATE Core/Inc App)
target_link_options(fw PRIVATE -T${CMAKE_SOURCE_DIR}/link.ld
    -Wl,--gc-sections -Wl,-Map=fw.map)
add_custom_command(TARGET fw POST_BUILD
    COMMAND arm-none-eabi-size $<TARGET_FILE:fw>
    COMMAND arm-none-eabi-objcopy -Obinary fw fw.bin)
# 使用： cmake -B build -DCMAKE_TOOLCHAIN_FILE=arm-toolchain.cmake && cmake --build build

11.5 原理深挖：Kconfig 的语义细节

select vs depends on：
  depends on A: 我只在 A 开启时可见（被动约束，用户可关我）
  select B:     我被选中时强制打开 B（主动拉依赖——可能违反 B 自己的 depends!）
  经典事故链： X select Y, 而 Y depends on Z 未满足 → 警告级破坏依赖
  实践准则： 库类符号允许被 select；策略类配置一律 depends on
defconfig 合并机制（Zephyr/IDF 同构）：
  prj.conf(你的) → 板级 defconfig → Kconfig.defaults 三层合并，
  后者只提供默认值；改板级默认应放 board.defconfig 而非手改生成物。

12.3 实战案例：10 分钟定位「变量被神秘篡改」

场景： g_state.mode 本该只被命令解析器修改，运行后莫名变成0xFF。

1) 先确认当前值与地址：
   (gdb) p &g_state.mode
   $1 = (uint8_t *) 0x20001a3c
2) 设硬件watchpoint（写触发）：
   (gdb) watch *(uint8_t*)0x20001a3c
   Hardware watchpoint 2: *(uint8_t*) 0x20001a3c
3) continue —— 第一次停下时 bt 看现场：
   #0 ... memcpy()            ← 凶手是某处memcpy！
   #1 sensor_dma_cb()
   结论： DMA缓冲越界写穿。检查缓冲尺寸与对齐（ch26）。
4) 若watch点不够用： 缩小范围二分——先watch整个结构体首字节，
   命中后再细化到成员；或临时把嫌疑数组加大32B填充哨兵值，
   watch哨兵变化即可锁定越界者。

12.7 原理深挖：断点家族的硬件真相

机制实现单元数量限制(M4)能做什么/不能什么
软件断点 BKPT改写指令存储无限(RAM)/只读区不可用停机后原指令由调试器恢复——Flash 上需擦写支持

数据观察点 DWT比较器×44 个地址/数据/读写方向匹配；CCM 等盲区无效(ch15)
RTOS 感知断点以上+符号脚本-按任务名下断：切任务时自动重装地址——纯 GDB 脚本可实现
单步的两副面孔：
  step-instruction: 目标机逐条执行(慢，每步一个往返)
  range-step:       告诉目标「跑到 PC>X 为止」硬件自己走(快，1次往返)
  next/step 高层命令 = 编译器行号表 + 这两种原语的编排
  反汇编窗口单步飞走？多半是行号表缺失(strip/-g丢失)而非芯片问题

12.10 进阶话题四则

  • checkpoint 思想：硬件不支持 reverse-debugging，但可以在关键节点把全 RAM dump 存档（dump binary memory），事后 restore 回去「倒带」复现——裸机版的时光机；

13.4 连接失败排查决策树

探针灯亮但找不到芯片？

13.6 原理深挖：SWD 连接时序与 connect-under-reset

标准连接序列：
① 主机在 SWCLK 上发 >50 个周期 SWDIO=1（line reset）
② 发 JTAG-to-SWD 切换序列 0xE79E770E(LSB先) + 再 line reset
③ 读 DP_IDR 验证链路活着 → 上电 DP/AP 电源域请求
connect-under-reset 为什么能救「睡死/引脚被抢」的芯片：
  NRST 拉低期间内核停摆但调试域仍供电 → 主机趁内核未跑用户代码
  （还没把 SWD 引脚复用成 GPIO）抢先完成握手 → halt 后再谈别的
OpenOCD 配方：
  reset_config srst_only srst_nogate connect_assert_srst
  adapter srst delay 100        # 复位保持 ms 数按板子 RC 调整

#define LOG_BUF_SZ 2048                 /* 2的幂 */
static uint8_t log_buf[LOG_BUF_SZ];
static ring_t log_ring = {log_buf,LOG_BUF_SZ,0,0};

void log_output(log_lv_t lv,const char*tag,uint32_t t,const char*fmt,...){
    char tmp[96]; int n=snprintf(tmp,sizeof tmp,"[%10lu][%c]%s: ",t,"EWID"[lv],tag);
    va_list ap; va_start(ap,fmt);
    n+=vsnprintf(tmp+n,sizeof(tmp)-n,fmt,ap);      /* snprintf保证不越界 */
    va_end(ap);
    if(n>=(int)sizeof(tmp)-2) n=sizeof(tmp)-2;
    tmp[n++]='\r'; tmp[n++]='\n';
    for(int i=0;i<n;i++){                          /* 单字节入队，满了丢新保旧 */
        if(!ring_put(&log_ring,tmp[i])){ log_dropped++; break; }
    }
}
/* 后台任务或SysTick里批量搬运到RTT/UART：

⚠️ 日志系统的四个经典坑

① 在 ISR 里同步 printf → 错过中断窗口引发新 Bug；② 缓冲区满时阻塞等待 → 实时任务被日志拖死（正确姿势：丢弃并计数 dropped++）；③ 多任务并发写 → 输出行交错撕裂（入队处关调度或用 SPSC+每任务私有缓冲）；④ 时间戳漂移 → tickless 低功耗下 tick 不连续，需补偿（ch50）。

15.2 堆健康度监控器

/* 包一层 malloc：统计 + 泄漏追踪 + 双重释放检测 */
typedef struct hdr { uint32_t magic,size,line; struct hdr*next; } hdr_t;
static hdr_t *g_allocs; static heap_stat_t g_stat;
void *xmalloc(size_t sz,int line){
    hdr_t*h = malloc(sizeof(hdr_t)+sz);         /* 生产版可换成FreeRTOS pvPortMalloc */
    if(!h){ g_stat.fail++; return NULL; }
    h->magic=0xDEADC0DE; h->size=sz; h->line=line; h->next=g_allocs; g_allocs=h;
    g_stat.cur_bytes+=sz; if(g_stat.cur_bytes>g_stat.peak) g_stat.peak=g_stat.cur_bytes;
    return h+1;
}
void xfree(void*p,int line){
    if(!p) return;
    hdr_t*h=(hdr_t*)p-1;
    if(h->magic!=0xDEADC0DE){ g_stat.bad_free++; return; }   /* 双重释放/野指针现行 */
    h->magic=0;
    for(hdr_t**it=&g_allocs;*it;it=&(*it)->next)
        if(*it==h){ *it=h->next; break; }
    free(h);
}
/* 周期任务打印： cur/peak/fail/bad_free + 存活分配按line聚类TOP5 —— 泄漏元凶一目了然 */

17.4 实战案例：MQTT 偶发断连定位

现象： 设备每30~60分钟随机掉线，日志只有 "mqtt disconnect"。
抓包： 板端 tcpdump host broker && port 1883 -w m.cap
分析： Wireshark Statistics→Conversations 按 Duration 排序；
     追踪 TCP Stream，发现断连前序列：
     [PSH,ACK] client keepalive publish → 无响应
     ... 15s 后 server 发 RST
     再往前翻： 大量 DupACK + 一段 60s 的静默期
结论链： 静默期=设备侧 lwIP 栈停摆（某任务长时间关调度）
      → 回到 MCU 用 DWT 测得 OTA 校验函数单次阻塞 62s
修复： 校验改分片+让步(vTaskDelay)，断连归零。
经验： 「网络问题」八成最终是本机软件问题——抓包给了证据链。

18.1 开机三件事

  2. 带宽与采样：奈奎斯特要求采样率≥2×信号频率，实际取 4~10 倍。DS1054Z 默认 1GSa/s 单通道足够；存储深度 M 固定时提高采样率会缩短记录时长——测低频长过程要主动降时基。
  3. 触发：默认 Auto（自由跑），测量稳定波形切 Normal 并设置边沿触发电平；抓偶发毛刺用 Pulse Width 触发（如 <100ns 正脉冲）；抓串口起始位用 Serial 解码触发。

18.2 场景一：UART 波形验证

接线： 探头地夹接GND，钩针接TX线（115200bps, 8N1）
设置： 时基 200µs/div；垂直 1V/div；Decode→UART→波特率115200→8bit无校验
判读：
  空闲电平=3.3V高；起始位=拉低1bit(8.68µs)
  LSB先行： 0x55=01010101b → 波形呈现交替方波（训练信号首选）
  波特率误差容忍≈±2%（两端都错就雪上加霜）—— 用光标量一位宽度和理论值比对
异常指纹：
  电平只到2V左右 → 上拉缺失/驱动弱/线太长分布电容大
  边沿爬升缓慢 → 加线端串联22~33Ω或降低波特率（ch28工程化对策）

18.3 场景二：I2C 时序体检

检查项合格标准（400kHz模式典型值）不合格后果
SCL 高电平时间≥0.6µs过短=上拉过强或驱动不足导致从机跟不上
上升沿时间<300ns（由 Rp×Cb 决定）过长→数据建立失败，表现为随机 NACK
总线空闲电平稳定 VDD半高不落底=有器件拉死总线（ch76解锁流程）
Clock Stretching从机可在SCL低保持主机不支持stretch却遇到会读错位——逻辑分析仪更易发现

操作要点：双探头同时挂 SCL/SDA，Decode 选 I2C 并填地址方向；用 Zoom 分屏放大到 NACK 附近逐位核对。

19.3 三大总线的解码判读

I2C

decoder 参数：sda/scl 通道，地址格式 7bit。健康事务的形状：START → ADDR+R/W → ACK(从机拉低) → DATA... → STOP。I2C 病灶速查表：

波形病灶根因候选处置
ADDR 后 NACK地址错 / 器件未上电 / 被其他主机占用核对 7bit vs 8bit 地址写法
DATA 中途 NACK从机忙（EEPROM 写周期！）或寄存器不存在写后 ack-polling 再继续
SCL 卡死在低从机 clock stretching 失控ch76 九步解锁流程
连续 START 重复主机重试风暴查上层超时参数

SPI

decoder参数： MOSI/MISO/CLK/CS + CPOL/CPHA模式 + 位序
高频陷阱： 模式配错时数据整体移位半个bit——解码出乱码但波形看着"正常"。
          对照器件手册时序图的第一个时钟沿采样位置逐一确认。
Flash调试利器： 解码出 9F(JEDEC ID) 命令后应答 EF4018...
              读ID不对→查WP#/HOLD#电平、QPI使能状态残留(ch77)

UART/RS485

decoder 参数：波特率/数据位/校验/停止位。RS485 再挂一路 A-B 差分需两通道算术相减——fx2 不支持数学通道，直接测 A 对地 + B 对地各一路，肉眼合成。

19.7 完整案例：I2C 读温感全程侦破（从乱码到修复）

案例：主机读 LM75 温度传感器，偶发读到 0xFFFF。

  1. PulseView @2MHz 采 SCL/SDA 各 5 秒，Add Decoder → I2C；
  2. 表格视图过滤 NACK：发现「写指针寄存器」后偶发 NACK；
  3. 展开该事务逐位看：STOP 后仅 0.4µs 就 START 下一次——而手册要求写后 tBUSFREE ≥ 4.7µs（SMBus），该器件需 1ms 写周期；
  4. 根因：驱动连发两条事务，未等待器件内部写完成；
  5. 修复：写后 ack-polling 循环（地址 ACK 即就绪）——复测 10 万次零错。

21.2 双栈与特权级

两个栈指针： MSP(主栈,复位默认) / PSP(进程栈)
两种模式： Thread(线程) / Handler(异常处理)
四种组合：
  Thread+MSP : 简单裸机（main和ISR共用一个栈）
  Thread+PSP : RTOS标配 —— 每任务独立PSP栈，内核/ISR统一走MSP栈
  Handler    : 永远用MSP，永远特权级
CONTROL寄存器 nPRIVASEL/SPSEL 位切换；
SVC 指令 = 用户态进入特权态的唯一正门（RTOS系统调用基础）

21.3 中断完整旅程（面试高频）

💡 EXC_RETURN 值速记

0xFFFFFFF1=Handler+MSP 返回；0xFFFFFFF9=Thread+MSP；0xFFFFFFFD=Thread+PSP（RTOS 任务被打断后的返回值）。bit2 判断用哪个栈恢复现场——这就是 ch05 取证代码里 tst lr,#4 的由来。带 FPU 的 M4F 还会懒压栈 FP 寄存器（FPCCR.ASPEN/LSPEN），入栈帧扩展到 26 字，栈预算记得加上。

21.4 启动流程四步曲

① BOOT 引脚采样(BOOT0/BOOT1)： 
     BOOT0=0 → Flash启动(常规)； BOOT0=1,BOOT1=0 → 系统bootloader(串口/USB ISP救砖)
     BOOT0=1,BOOT1=1 → SRAM启动(调试用)
② 向量表定位： SCB->VTOR 可重定位（IAP双程序区的关键，ch30）
③ Reset_Handler(ch06已精读)： 设栈→SystemInit(时钟)→data/bss→__libc_init_array→main
④ main 前 C 库初始化 __libc_init_array 会跑全局构造(C++)与 .init_array 表

21.8 原理深挖：EXC_RETURN 完整位域与 FPU 懒压栈

bit含义常见组合值解读
[31:5]固定 0xFFFFFFF 前缀-

FPU 懒压栈(Lazy Stacking)三步舞：
① 任务用了 FPU 且 FPCCR.ASPEN=1 → 异常入栈时先在栈上预留 FP 帧
② 若该异常处理不用 FPU → 只写 FPCCR.LSPACT 标志，FP 寄存器不真压(懒)
③ 处理器若要用 FPU → 触发懒保存故障，此时才把 s0~s15 补压进保留帧
收益： 中断延迟从「+17字压栈」降到固定开销；代价： 栈预算必须按满帧 26 字算！

/* UART_HandleTypeDef 拆解 —— 读懂它=读懂 HAL 的设计哲学 */
typedef struct __UART_HandleTypeDef {
  USART_TypeDef        *Instance;    /* 寄存器基址——指向物理世界的唯一窗口 */
  UART_InitTypeDef     Init;         /* 你的配置参数(波特率/字长/…) */
  uint8_t              *pTxBuffPtr;  /* ┐ */
  uint16_t             TxXferSize;   /* ├ 运行期传输状态机的工作区 */
  volatile uint16_t    TxXferCount;  /* ┘ (volatile: ISR 会改它) */
  void (*RxISR)(...);               /* 中断处理函数指针——HAL 内部多态! */
  DMA_HandleTypeDef    *hdmarx;      /* 关联 DMA 句柄 */
  HAL_LockTypeDef      Lock;         /* 粗粒度锁(仅防重入, 非线程安全!) */
  __IO HAL_UART_StateTypeDef gState, RxState;
} UART_HandleTypeDef;
/* 推论：
   ① 多任务并发调 HAL_UART_Transmit 同一句柄会互踩——锁只保护状态位

23.7 原理深挖：BSRR 原子性的汇编证据

; ODR 读改写(非原子) 编译产物：
    ldr  r1, =0x40020014
    ldr  r2, [r1]        ; ① 读 —— 若此处被打断且 ISR 改了同寄存器…
    orr  r2, r2, #0x200  ; ② 改
    str  r2, [r1]        ; ③ 写回 —— 覆盖 ISR 的修改！竞态窗口 3 条指令
; BSRR 单指令写(原子)：
    movw r2, #0x0200     ; 置位/复位编码在同一写动作里完成
    ldr  r1, =0x40020018 ; BSRR 地址
    str  r2, [r1]        ; 一条 str，硬件保证无中间态
; 结论： 多位同时操作或 ISR 共享引脚场景，BSRR 是唯一正确选择

24.1 优先级体系全景

概念规则F407 取值
抢占优先级 Preemption数值越小越优先，可打断正在执行的低级 ISR分组决定位数
子优先级 Sub只在同时 pending 时排队顺序起作用，不能抢占同上互补
IRQ 编号两者相同才比较0~81
分组 NVIC_PriorityGroup整个工程统一设置一次推荐 Group4：4位抢占+0位子（FreeRTOS 只用抢占）
⚠️ FreeRTOS 黄金法则

configMAX_SYSCALL_INTERRUPT_PRIORITY(默认5) 以上的中断（数值更小如 0~4）可以打断 RTOS 内核，但禁止调用任何 FromISR API。把需要用队列/信号量的 ISR 优先级设为 5~15，违反则出现神秘 HardFault——这是 FreeRTOS 新手第一大坑。SysTick/PendSV/SVC 固定最低 15。

24.3 临界区三种姿势

/* 姿势1 全局关中断（粗暴，短临界区专用）*/
uint32_t pm=__get_PRIMASK(); __disable_irq();
/*...*/ __set_PRIMASK(pm);                  /* 保存恢复而非盲开——支持嵌套 */

/* 姿势2 屏蔽特定优先级以下(BASEPRI) —— FreeRTOS taskENTER_CRITICAL 本质 */
__set_BASEPRI(5<<4);                       /* 5~15全闭，0~4仍能响应 */
__set_BASEPRI(0);

/* 姿势3 RTOS互斥量（长临界区/可能阻塞场景）*/
xSemaphoreTake(mtx,portMAX_DELAY);
/*...含耗时操作甚至API调用...*/
xSemaphoreGive(mtx);
选型口诀： 几条指令→姿势1/2；跨函数或含阻塞→姿势3；
ISR里绝不能用姿势3(xSemaphoreTake会断言)！ISR只有 FromISR 不阻塞版本。

/* configMAX_SYSCALL_INTERRUPT_PRIORITY=5 如何变成硬件行为：

24.10 进阶话题四则

  • 软触发的正确用法：STIR 只对特权级有效且 IRQ 号要减 16 偏移写错就静默无效——用它做单元测试注入比改硬件跳线优雅得多；

  • 优先级分组只设一次：HAL_Init 里设 Group4 后任何库再改分组都会让你的 IPR 解读错位——CI 加 grep 防二次配置。

25.2 时基与 PWM 计算公式（背下来）

/* 溢出周期 = (PSC+1)*(ARR+1)/Tclk */
/* 例： 84MHz, PSC=83, ARR=999 → 更新中断频率 = 84e6/(84*1000) = 1kHz */

/* PWM 频率 = Tclk/(PSC+1)/(ARR+1) ； 占空比 = CCR/(ARR+1) */
TIM3->PSC = 83;                 /* 84M/84 = 1MHz 计数节拍 */
TIM3->ARR = 999;                /* PWM 频率 = 1kHz */
TIM3->CCR1 = 250;               /* 占空比 25% */
TIM3->CCMR1 |= 6<<4;            /* OC1M=110 PWM模式1： CNT<CCR输出有效电平 */
TIM3->CCER |= 1<<0;             /* 使能CH1输出 */
TIM3->CR1 |= 1;                 /* 启动 */
/* 高级定时器额外项： RCR重复计数器(降低更新率)、BDTR死区=两管切换安全间隔
   死区计算： DTG位域编码，如 CKD=00时 DTG[7:5]=000 → DT=p*DTG[7:0]*TDTS */
⚠️ PWM 调光闪烁之谜

PWM 频率低于人眼临界值(<100Hz)或落在相机快门频段就会「闪」。LED 呼吸灯建议 ≥1kHz；驱动风扇注意低频段的啸叫（线圈振动），常见解法把频率提到 20kHz 以上——此时 ARR 变小分辨率下降，权衡公式：分辨率位数=log2(Tclk/fpwm)。

25.6 原理深挖：预装载寄存器与影子寄存器

/* 为什么有时改 CCR 立即生效，有时要等下个周期？
   CCR/ARR 有「预装载」影子机制： ARPE=1 时你写的是预装载寄存器，
   在更新事件(UEV)才同步进影子寄存器(真正参与比较的那个)。
   ARPE=0 → 写入直达影子 → 立即生效但可能产生畸形脉冲！
   PWM 相位连续性要求 → 标准姿势： ARPE=1 + 周期首改参数 */
TIM3->CR1 |= TIM_CR1_ARPE;      /* 使能 ARR 预装载 */

25.9 进阶话题四则

  • 中心对齐的价值：计数三角波使 PWM 脉冲居中对称——电机相电流采样窗口天然落在中心，纹波最小（FOC 必选）；
  • 死区的精确计算：DTG[7:5]=0xx → DT=DTG[7:0]×Tckts; 以 168M/2=84ns 步进，设 1µs 死区即 DTG≈11——用示波器量两管波形验证而非纸面自信；
  • 单脉冲模式(OPM)：触发一次输出一个受控宽度脉冲——超声波测距/相机快门的标准硬件方案，CPU 只管触发；
  • ETR 外部时钟：定时器可拿外部引脚做时钟源——高频事件计数不占 CPU，比 EXTI 中断数沿快两个数量级。

27.1 F407 ADC 关键规格

12位 SAR ×3个ADC，可独立/双重/三重交织(最高7.2Msps聚合)
转换时间 = 采样时间(3~480 cycles) + 12 cycles(转换)
例： PCLK2/4=21MHz, 采样15cycles → (15+12)/21MHz ≈ 1.29µs ≈ 777ksps
VREF+ 通常接 VDDA(3.3V)，精度型应用外接基准芯片(REF3033 0.05%)
输入范围 0~VREF+；内建 VBAT/VREFINT/温度传感三个内部通道自检

27.2 采样时间与信号源阻抗

信号源阻抗 RAIN最小采样周期(@PCLK2=21M)工程含义
50Ω（运放直驱）~3 cycles低阻源随便采
10kΩ（电位器分压）~36 cycles中等，默认设置可用
50kΩ（热敏电阻）~112 cycles必须加长采样或加缓冲运放
💡 采样保持电容模型

ADC 内部有 ~4pF 采样电容通过开关接入引脚，采样窗口内要通过 RAIN 给它充满。RAIN 太大充不满 → 读数偏低且随相邻通道「串味」（残留电荷）。对策排序：加长采样时间 → 引脚到地加 1~10nF 电荷池电容（兼滤高频）→ 前级加轨到轨运放跟随器。

27.4 过采样降噪与校准

/* 过采样定理： 4N次采样平均提升N位有效分辨率(需噪声≥1LSB存在) */
uint32_t oversample_adc(uint8_t ch,uint8_t extra_bits){
    uint32_t n=1u<<(extra_bits*2),acc=0;
    for(uint32_t i=0;i<n;i++) acc+=read_once(ch);
    return acc>>extra_bits;                    /* 16次采12位→14位有效 */
}

28.6 原理深挖：IDLE 检测的硬件本质与 TC/TXE 之辨

/* IDLE 位何时置起？
   接收移位器在 RxD 连续保持 1 个完整字符时间的高电平后置 IDLE——
   「一个字符时间」= 当前波特率自适应，这就是它比固定 µs 定时优雅的原因 */
/* TXE vs TC 的精确语义：
   TXE(Transmit Data Empty): 数据已从 DR 拷进移位器 —— 可写入下一字节
   TC (Transmission Complete): 移位器也空了，线上最后一位已移出
   → 连续发送看 TXE； 切 RS485 方向/关时钟必须等 TC！*/
while(!(USART1->SR & USART_SR_TXE)); USART1->DR=b;   // 流水发送
while(!(USART1->SR & USART_SR_TC));                  // 尾部等待

28.7 完整工程：协议帧解析器 parser（零拷贝喂入式）

/* frame_parser.h —— 与接收通道解耦的可复用状态机 */
typedef enum {P_HEAD,P_LEN,P_PAYLOAD,P_CRC} p_st_t;
typedef struct {
    p_st_t st; uint8_t buf[280]; uint16_t idx,len;
    void (*on_frame)(uint8_t*,uint16_t);
} parser_t;
void parser_feed(parser_t*p,const uint8_t*d,int n){     /* 喂任意长度片段 */
    while(n--){
        uint8_t b=*d++;
        switch(p->st){
        case P_HEAD: if(b==0xAA){p->buf[0]=b;p->idx=1;p->st=P_LEN;} break;
        case P_LEN:  p->len=b; p->buf[p->idx++]=b;
                     p->st=(b<=255)?P_PAYLOAD:P_HEAD;   /* 非法长度即复位 */
                     if(p->st==P_PAYLOAD&&p->len==0)p->st=P_CRC; break;
        case P_PAYLOAD: p->buf[p->idx++]=b;
                        if(p->idx==p->len+2u)p->st=P_CRC; break;
        case P_CRC: p->buf[p->idx++]=b;
                    if(p->idx==p->len+4u){
                        if(crc16(p->buf,p->idx-2)==
                          (p->buf[p->idx-2]|p->buf[p->idx-1]<<8))
                            p->on_frame(p->buf+3,p->len);   /* 校验通过派发载荷 */
                        p->st=P_HEAD; }
                    break; }}}
/* 设计要点： 任何非法输入都回到 P_HEAD 自愈； 超时清理由上层用 IDLE 触发 */

29A.1 三种电源事件对照

机制触发点行为软件可见性
POR/PDR上电/掉电阈值(~1.7V)保持复位直到电压稳定不可见——纯硬件保护
BOR可配阈值(2.0~2.9V)欠压即复位复位后 CSR 标志可读
PVD ★软件主角可配阈值(2.2~2.9V)仅产生 EXTI 中断提前预警，可抢救
设计逻辑链：
PVD 阈值设为「比最低工作电压高 ~0.3V」 → 电压跌到此处时
CPU 还能全速跑几百 µs~几 ms（取决于储能电容） → 这段窗口用来：
① 关闭写入中的 Flash/DMA ② 把易失状态压进 NoInit 区/备份域
③ 发出「即将死亡」日志 ④ 可选：拉高某 GPIO 通知上位机
BOR 作为最后防线兜底 —— PVD 抢救失败也不至于写出半截 Flash。

30.2 跳转代码精读（每个字都有理由）

#define APP_ADDR 0x08008000
typedef void (*pFunc)(void);
void jump_to_app(void){
    uint32_t sp=*(volatile uint32_t*)APP_ADDR;          /* APP栈顶指针 */
    uint32_t pc=*(volatile uint32_t*)(APP_ADDR+4);      /* Reset_Handler地址 */
    if((sp&0xFF000000)!=0x20000000) return;             /* 栈顶合法性快检(SRAM区) */
    __disable_irq();
    for(int i=0;i<8;i++) NVIC->ICER[i]=0xFFFFFFFF;      /* 关所有中断 */
    for(int i=0;i<8;i++) NVIC->ICPR[i]=0xFFFFFFFF;      /* 清所有pending */
    SysTick->CTRL=0;                                    /* 停SysTick防中途异常 */
    SCB->VTOR=APP_ADDR;                                 /* 向量表指过去(ch24) */
    __set_MSP(sp);                                      /* 切主栈！ */
    ((pFunc)pc)();                                      /* 跳转，一去不返 */
}
/* APP 侧配套： SystemInit 前 SCB->VTOR 已被boot设置？保险起见APP自己再设一遍；
   链接脚本 FLASH ORIGIN=0x08008000 LENGTH 同步收缩；
   中断向量表内容整体平移——这就是为什么APP的bin不能直接烧0地址 */

30.4 MCUboot：安全升级工业标准

核心概念（github.com/mcu-tools/mcuboot，Zephyr/Mynewt默认引导）：
① 镜像头 TLV： 版本号/哈希(SHA256)/签名(ECDSA-P256 或 RSA2048)
② swap-move 交换算法： 两slot原地互换，中断任意时刻掉电都能恢复一致性
③ 三态标志 pending/confirmed/revert：
   下载新固件→标TESTING→重启进新版自证OK后 confirm
   若新固件起不来（喂狗超时/连续复位计数超限）→ 自动revert回旧版 ★生产刚需
④ 私钥签发在产线服务器，设备端只放公钥哈希 —— 私钥泄露风险归零
接入路径： Zephyr west build -b ... --sysbuild 直接集成；
          STM32裸机项目参考 mcuboot 的 bootutil 库移植指南。

30.6 原理深挖：swap 算法的掉电一致性状态机

slot0(A) 与 slot1(B) 互换时，param 区(trailer)记录进度日志：
  状态序列： SWAP_START → 写A→暂存B的每扇区前先记录「第n步」
           → 任意时刻掉电，重启后 bootloader 读到「第n步」
           → 从该步继续（幂等：重做同一扇区写入是安全的）
  完成态标记 SWAP_DONE 后清日志。
不变量： 任何一步中断，两 slot 内容组合起来总能恢复出
        「旧固件或新固件之一完整可用」——这就是「永不变砖」的数学保证。
scratch 区的作用： 交换时的中转站；无 scratch 变体直接在两 slot 内轮转，
  省空间但算法更绕(参考 mcuboot swap-move 论文注释)。

}

30.10 进阶话题四则

  • 防降级的版本存放：单调计数器放 OTP/备份域而非参数区——参数区可被整片擦除伪造；每次升级 +1 且新固件必须 ≥ 计数值；
  • 差分升级(bsdiff)的 MCU 移植：解压需要约 1×新旧镜像之一的 RAM 工作区——小 RAM 设备改用分块 VCDIFF 或整包压缩；
  • A/B 指针式替代真交换：不搬数据只改「启动槽指针」，代价是两份常驻空间——H7 双 Bank 与 ESP32 都是此思路，时间成本趋零；
  • 恢复模式的最小实现：Bootloader 里常驻一个「仅收 Ymodem 的极简接收器」——App 全灭时仍有一条生路，代码预算 ~8KB。

32.4 功耗要点

  • Modem sleep：STA 空闲时关 RF，电流从 ~70mA 降到 ~3mA（DTIM 唤醒）；

  • BLE 广播间隔与连接参数直接决定平均功耗——1s 广播比 20ms 省 50 倍。

T2：MQTT 偶发 broker 连接成功但发布丢失？

QoS0 不保证送达。改 QoS1+本地 seq 去重；断网期缓存队列上限要设，防止内存被补传撑爆。

T3：SHT31 读数偶发 0xFF 全 F？

I2C 总线干扰或上拉不足。先示波器看边沿(ch18)；软件侧加 CRC 失败重试 2 次+连续失败告警；总线卡死走 ch76 解锁流程。

T4：老化 24h 后 heap 剩一半？

九成是 JSON 组包用完没释放(cJSON_Delete)。heap_caps 跟踪每个 malloc 调用点的存活数，泄漏元凶按行号聚类秒现形。

33.10 进阶话题三则

  • 双平台抽象的收益兑现：App 层零改动跑在 F407 与 ESP32-S3 上——验证你 ch08 分层的成色，也是简历上的硬核亮点；
  • 从终端到系统的演进路线：本项目 → 加 RS485 变网关(ch44) → 上 RTSP 变监控节点(ch66)——同一套骨架的三次变现；

一分钟闭卷

先自问，再翻讲义
  1. 工具链是一组假设
    闭卷自问：为什么 arm-none-eabi 工具链编不出 Linux 用户态程序？
    展开答案要点

    架构、ABI、浮点 ABI、libc 与 sysroot 任何一项不匹配，都会在编译、链接或运行期爆炸。

  2. 可执行文件自带地址观
    闭卷自问：向量表为什么通常必须位于 Flash 起始地址？
    展开答案要点

    链接脚本决定 .isr_vector/.text/.data/.bss 落在哪；启动文件负责把 .data 搬进 RAM、把 .bss 清零。

  3. 崩溃现场可以取证
    闭卷自问：如何从 MSP/PSP 栈帧找到出错时的 PC？
    展开答案要点

    HardFault 栈帧、CFSR/HFSR、MMFAR/BFAR 加上 .map 与反汇编，能把异常落到具体指令。

  4. 时序必须用仪器说话
    闭卷自问：I²C 的时钟拉伸在示波器上是什么形态？
    展开答案要点

    示波器看电源与边沿，逻辑分析仪解码总线，频谱仪看 EMI；不要用 printf 猜时序。

  5. 外设配置最终落到寄存器
    闭卷自问：DMA 写内存后 CPU 读到旧值，是谁的缓存没有维护？
    展开答案要点

    时钟树、NVIC、DMA 与 Cache、ADC 采样时间，每一层都能在寄存器与波形上验证。

  6. 产品能力在边界处见真章
    闭卷自问：升级中断电，重启后靠什么判断该继续还是回滚？
    展开答案要点

    低功耗、掉电保护、双分区 OTA 与回滚，决定原型能不能变成可交付设备。

高频追问 · 先答后看

5 问
`-O2` 下 `while(!flag)` 循环消失或变成死循环，为什么？volatile 到底管什么？

编译器假定普通变量不会被当前执行流之外的因素改变，因此可以把读取提升或删除。volatile 强制每次都从内存访问，阻止这类优化；但它不提供原子性与内存序。若变量同时被中断、DMA 或另一个核修改，还需要屏障、原子操作或正确的同步原语。

HardFault 发生后，怎样在 5 分钟内定位到源码行？

先在异常入口保存 MSP/PSP 与 r0–r3、r12、lr、pc、xPSR，再读 CFSR/HFSR/MMFAR/BFAR 判断异常类型；用栈帧里的 PC 对照 .map 与反汇编定位函数和指令；最后检查指针、栈水位、MPU 配置与外设时钟。关键是先保存现场，再重启。

DMA 与 Cache 为什么会导致数据不一致？正确顺序是什么？

DMA 绕过 CPU Cache 直接读写内存，CPU 可能命中旧 cache line。接收方向应在 DMA 完成后、CPU 读取前 invalidate；发送方向应在 CPU 写完、启动 DMA 前 clean。缓冲区按 cache line 对齐，避免一行内混合 CPU 与 DMA 的数据。

双分区 OTA 如何保证任意时刻掉电都不变砖？

升级只写非活动分区，写完先校验哈希/签名，再用带序号与状态位的 boot 元数据原子切换；元数据本身要双副本加 CRC。新固件启动失败计数达到阈值就回滚，运行中的分区永远不被覆盖。最后用断电注入验证，而不是只测正常升级。

为什么 ISR 里不能调用 printf、malloc 或可能阻塞的函数？

这些函数可能加锁、不可重入、触发缺页或长时间忙等，会拉高中断延迟甚至死锁。ISR 只做清标志、搬少量数据、发信号，重活交给线程、workqueue 或下半部；日志先写入无锁环形缓冲，再在上下文允许时输出。
