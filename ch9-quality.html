9.5 · 质量门禁

同一条缺陷，越晚发现越贵

选择一种缺陷注入，然后运行流水线。编译、静态检查、单元测试、覆盖率和 HIL 各拦一类问题；第一道失败的门就会终止发布。真正要建立的能力，是知道“该由哪道门拦住它”。

门禁的意义不是“更严格”，而是“更早”。编译器能抓的绝不留给 reviewer，单测能抓的绝不留给 HIL。每一层只承诺它擅长的那类缺陷。
个人项目最低配三件套：-Werror + Unity 主机测试 + cppcheck --enable=warning。半天投入，换每次重构都有安全网。
门禁会失败，流程不能靠人记：把命令写进 Makefile / CI，失败即阻断合并；本地能用 make check 一条命令复现，才不会出现“CI 挂了但我本地是好的”。
9.1 · MISRA C:2012

不要背条款，先理解每条规则在防哪种事故

下面六行代码各踩一条高频 MISRA 规则。点击任意一行，查看规则编号、真实动机和修复方式；逐条修复后，报告从 6 条降到 0 条。企业落地时，先卡 mandatory 条款的增量代码，存量按目录分批清零。

代码诊所：UART 采样模块

6 处违规
点击左侧红色行号

每一行对应一条规则。重点不是记住编号，而是能说出：如果不改，会在什么场景下出错？

误报怎么办？行内豁免必须带理由，而不是全局降级：
// cppcheck-suppress misra-c2012-11.3 ; 已评审的 DMA 对齐方案

必懂条款 TOP 6

先懂动机
R10.x 隐式类型转换
有符号/无符号混算是 C 最深的坑，显式转换让意图可审查。
R11.x 指针强转
别名与对齐违规会破坏优化假设，DMA / 寄存器映射是重灾区。
R17.7 返回值必须使用
忽略 write()/memcpy() 返回值，等于把错误静默丢掉。
R18.x 指针运算受限
数组越界是 UB 重灾区，长度必须来自同一处可信来源。
R13.6 sizeof 不得有副作用
sizeof(i++) 的求值次数不可靠，跨编译器结果会变。
R21.x 禁用裸 malloc
动态内存让最坏执行时间不可分析；嵌入式优先静态池。
单一出口是讨论项，不是教条。R15.5 的动机是便于插桩与资源回收；现代实践允许提前 return + RAII / goto cleanup，但必须保证所有路径释放资源。
9.2 / 9.7 · 静态分析工具链

没有一把工具能通吃，正确姿势是双轨并行

选一个缺陷样本和一把工具，看看它是否检出、报了什么。MISRA 合规用 cppcheck + 插件；逻辑缺陷交给 clang-tidy 或 GCC -fanalyzer。工具的价值不在于“零误报”，而在于稳定地重复审查。

结论：MISRA 合规用 cppcheck --addon=misra.py；逻辑缺陷用 clang-tidy 或 -fanalyzer。两轨并行，互相补盲，误报用行内豁免治理。
工具也会漏：检出率来自注入样本，不代表真实项目。静态分析是“稳定复查”，不能替代边界测试与 HIL。 
# 一条命令产出 MISRA 报告
cppcheck --enable=all --inline-suppr \
  --addon=misra.py -I inc src/ 2> misra_report.txt

# clang-tidy 可自动修复
clang-tidy src/app_sensor.c \
  -checks='bugprone-*,performance-*' --fix \
  -- -Iinc --target=arm-none-eabi -mcpu=cortex-m4
9.3 / 9.4 · Unity + CMock

在主机上把逻辑跑穿，再用桩把硬件隔开

Unity 负责断言与测试夹具，ASan 把越界当场爆出来；CMock 负责“预期调用”——业务代码以为自己在调驱动，其实在调桩。先运行一次全绿的测试，再注入 bug 看它们如何失败。

环形缓冲区测试集

主机 gcc + ASan

test_full_rejects待运行
test_wraparound待运行
test_null_buffer_rejected待运行
UNITY_BEGIN ... 等待运行
setUp / tearDown：每个用例前重建夹具，避免用例之间共享状态。测试必须能单独运行、任意顺序运行。

CMock：硬件调用的“剧本”

期望 2 次调用
被测：link_send_hello()
bsp_uart_send(UART1, "AT+HELLO\\r\\n", 11, 0)—
bsp_uart_send(UART1, "AT+JOIN\\r\\n", 10, 0)—
待运行：CMock 将比对“期望调用”与“实际调用”的参数、次数和顺序。
桩的粒度：函数级 mock（CMock）适合驱动边界；模块级假实现（Mock 传感器）更适合业务规则。先想清楚“要隔离哪种不确定性”。
ASan 误伤第三方库？用 -fsanitize-blacklist 排除无法重编的库，或把该模块的 sanitizer 单独关闭——不要因此关掉整个测试集的 sanitizer。
9.8 / Lab L9-1 · 覆盖率

覆盖率不是分数，是“哪些分支还没被质疑过”

选择测试用例，观察 q15_mul 的哪些行被执行。80% 是常见门槛，但真正的目标是补上饱和、零值、边界这些最容易出错的分支。试着补齐正、负饱和用例，看红色行如何消失——注意 80% 行覆盖仍可能漏掉关键边界。

CI 门禁最小集

GitHub Actions
name: fw-ci
on: [push, pull_request]
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: sudo apt-get install -y \
          gcc-arm-none-eabi cppcheck lcov
      - name: Build firmware
        run: make all          # -Werror
      - name: Unit tests
        run: make test         # Unity + ASan
      - name: Static analysis
        run: cppcheck --error-exitcode=1 \
          --enable=warning,performance -Iinc src/
      - name: Coverage gate
        run: ./scripts/cov_gate.sh 80
最小集就够跑起来：编译 + 单测 + cppcheck warning。覆盖率与 MISRA 增量门禁第二步再加，避免一开始被几千条存量报告淹没。
主机测试过、上板就崩？测试替身掩盖了时序/中断/对齐问题。主机测逻辑正确性，板级另建 HIL 冒烟集（上电→自检→心跳），两层缺一不可。
