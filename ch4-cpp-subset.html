什么时候值得用 C++？选型判断

        

          
适合：模块超过 20 个、有多个状态机/协议栈/UI 的中型项目；需要接口抽象与主机测试的团队。

          
不适合：几百行、单文件、生命周期极短的小固件；C 更轻、更直接。

          
常见混合：驱动层 C 对接厂商 HAL，业务层 C++ 子集；边界用 extern "C" 桥接。

        

      

      

        
零开销抽象 ≠ 零成本本章主线

        
封装、RAII、constexpr 通常没有每对象开销；模板会增加实例化代码，虚函数会增加 vptr 和间接调用，异常/RTTI 会带入表与元数据。“零开销”指你不用的东西不付费，不是所有抽象都免费。

        
记账顺序：对象隐藏字段 → 链接器带入的代码 → 运行路径是否确定。先看这三处，再谈优化技巧。

为什么 RAII 能覆盖所有出口语言保证

        
析构由作用域结束触发，而不是由某个 return 触发：正常返回、提前返回、break/continue、goto 跳出、异常展开，都会销毁已构造的自动对象。你不需要在每个出口复制清理代码。

        
顺序记忆：先构造的后析构。栈帧里的资源像叠盘子，最后放上去的最先拿下来。

      

      

        
goto cleanup 的问题不是“错”，是“脆”可维护性

        
goto cleanup 在 C 里可以完全正确；问题是每新增一个资源，都要记得在 cleanup 块里按逆序释放，还要保证所有路径都跳到那里。RAII 把这套纪律变成类型和析构函数，新增成员时自动生效。

        
别把 RAII 当“自动 goto”：它只管理生命周期明确的资源；动态数组、引用计数和共享所有权仍要单独设计。

构造不失败两段式

        
构造函数只做“不可能失败”的取得；可能失败的操作放到 begin() / 工厂，返回 bool 或错误码。对象构造完成，但“是否可用”由 begin() 报告。

      

      

        
资源交给成员失败也能回收

        
不要在构造函数体内裸拿资源再保存到裸指针；把 CS、总线锁、DMA 句柄做成成员对象。成员按声明顺序构造、按逆序析构，失败路径也不会漏。

      

      

        
ScopeExit 的模板税C API 清理

        
模板版 ScopeExit 为每个 lambda 类型生成一份代码；函数指针版省 Flash 但丢捕获。热路径优先显式守卫类，C API 清理才用 ScopeExit。

      

    


    

      异常路径的额外规则：若项目开启异常，构造函数抛出时，对象自身的析构函数不会执行，只有已经构造完成的成员会析构。因此资源必须由成员对象持有，而不是在构造函数体里手工获取后等析构函数来善后。

这笔钱什么时候值得花决策

        

          
值得：驱动可替换、主机测试替身、运行期换实现；接口窄、对象数量适中时，vptr 成本很低。

          
不值得：ISR 热路径、成千上万个微小对象、每个对象只有一个实现；这时函数指针或模板注入更合适。

          
能省掉：类型已知或类标记 final 时，编译器可能去虚化并内联；不要假设一定发生，用 objdump 验证。

          
多重继承：通常每个多态基类子对象一个 vptr，还要做 this 调整；接口用纯虚单继承，避免多重继承。

局部 static 与全局析构两个容易忽略的边界

Sensor& sensor() {
    static Sensor s;
    return s;
}

// -fno-threadsafe-statics 后：去掉 guard
// 裸机单线程 / 调度器启动前首次调用 → 可安全
// RTOS 多任务并发首次调用 → 可能重复构造

        

          
✓RTOS 下：在创建任务之前完成首次调用，或用显式 init()。

          
✓全局对象只做平凡初始化；硬件操作放 begin()，在 board_init() 之后调用。

          
✓main 通常不返回，静态析构不保证执行；硬件关闭用显式 shutdown()。

        

      

    

  


  
  

    

      
4.7故障排查：Flash、启动、HardFault 与 new

      
C++ 的问题常常不是语法错误，而是“链接器悄悄拉进来一大段”或“构造函数在错误的时机跑了”。这一节用符号表、启动时序和最小复现来定位。

    


    

      

        
Flash 法证：先看符号，不要猜示例输出

        
$ arm-none-eabi-nm --size-sort -C fw.elf | tail -20

        

          
          
        

        

        
点击一行查看对应的“删/换/限”处理。符号名与体积为示意，真实数值以你的 ELF 为准。

      


      

        
ISR、new/delete 与 HardFault运行时边界

        

          
          
          
        

        

        

      

    


    

      

        Flash 占用暴涨几百 KB
        
根因：iostream/locale 被拉入；模板过度实例化；异常表或 RTTI 残留；printf 浮点格式。定位：nm --size-sort -C 找大符号，size -A 看段分布；关异常/RTTI、去 iostream、限制模板类型数量、启用 section GC。

      

      

        启动卡死在 static 初始化
        
根因：全局对象构造函数依赖外设/时钟/RTOS，而这些还没初始化。定位：在 __libc_init_array 前后打点（早期 UART 轮询），检查 .init_array；改为全局平凡初始化 + begin() 两段式。

      

      

        ISR / 回调里偶发 HardFault
        
根因：ISR 与 C++ 函数签名/链接名不匹配；构造期间调用虚函数；纯虚调用；ISR 里使用堆、阻塞锁或过长路径。定位：用 extern "C" 桥接，检查向量表与反汇编；读 CFSR/HFSR/BFAR/MMFAR 和异常栈帧，再 addr2line 定位。

      

      

        new 返回野指针 / 堆与内存池冲突
        
根因：没有重载全局 operator new/delete，默认落到 malloc；池分配器与 C 库堆各自管理同一块内存。定位：重载并统一到池；链接 --wrap=malloc 校验；更彻底的做法是禁用动态分配，改用静态池 + placement new。

      

    


    

      

        
FAQ：裸机项目有必要用 C++ 吗？选型

        
看团队与规模：模块超过 20 个、有状态机集群/UI 的中型项目，C++ 子集收益明显；几百行的小固件 C 更轻快。混合方案很常见——驱动层 C 对接 HAL，业务层 C++。

      

      

        
FAQ：异常真的绝对不能用吗？边界

        
M 核硬实时默认禁用。A 核 Linux 应用进程内可用；原则是资源受限 + 硬实时 = 禁，富资源 + 软实时 = 可议。禁用异常后，用返回码 + RAII 管理错误路径。
